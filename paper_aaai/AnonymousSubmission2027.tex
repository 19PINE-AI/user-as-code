\begin{abstract}
An agent that remembers 100 trips should answer not only where a user traveled, but how often they visited Europe. Textual memories accessed through top-$k$ retrieval can recover individual trips but cannot reliably enumerate all of them, while conventional structured stores require a domain model to be defined and maintained. We introduce \textbf{User as Code} (UaC), which appends session facts and periodically materializes an LLM-generated typed Python view while retaining fact and archive channels for recall. Across all 1{,}986 LOCOMO annotations in each of two model panels, UaC achieves the highest same-backbone judge accuracy among the evaluated persistent-memory systems: 78.8\% with GPT-5.6 Luna and 80.6\% with Gemini~3 Flash Preview on the 1{,}540 answer-bearing questions. Token F1 on those questions (39.4\%/46.9\%) and refusal accuracy on 446 adversarial questions (64.3\%/95.7\%) expose metric-specific tradeoffs. On 100 deterministically scored aggregate queries, both UaC and a raw-record Full Context+REPL reference reach 100\%, versus 43\% for MemMachine and 6\% for Mem0. The results show that an enumerable, code-readable representation enables reliable aggregate queries while remaining compatible with retrieval-based factual memory.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Consider a personalized agent whose memory contains 100 trips accumulated across years of conversation. The user may ask, ``Where did I stay in Paris?'', but also ``How many times have I traveled to Europe?'' or ``How many trips did I take in 2025?'' The first question may be answered from one relevant memory. The latter questions generally require enumerating the complete trip history, filtering it, and counting the matching records: omitting even one trip can change the answer. Memory can also matter without an explicit query: if a stored passport expires before a newly mentioned departure, the agent should surface the conflict without being asked for a reminder. These examples expose three demands on long-term memory: factual recall, complete-set inference, and cue-free evaluation of persistent constraints, in which a later memory update triggers a check without an explicit reminder request.

Most agent-memory systems store conversations as text, extracted facts, linked notes, or graphs and answer questions through top-$k$ retrieval. This interface is effective when the answer appears in one or a few records, but retrieval is designed to return the most relevant evidence, not to enumerate a complete collection. Once the number of relevant records exceeds $k$, an exact count or aggregate becomes unreliable. Passing the entire history to the model restores access to the records, but incurs growing context cost and still asks the model to parse and count them in-context. Existing long-term-memory benchmarks likewise emphasize query-driven recall~\citep{maharana2024locomo,wu2025longmemeval,hu2025memoryagentbench} rather than complete-set computation.

A conventional structured database addresses the computational problem only after a suitable data model has been provided. For the travel example, a developer might define a \texttt{Trip} table with dates, countries, and regions, after which the desired counts are straightforward. A general personal agent, however, encounters evolving information across travel, health, finance, relationships, and domains not known in advance. Requiring developers to anticipate and maintain a schema for every such domain turns open-ended user memory into an ontology-engineering problem. Although database schemas can be migrated, the system still needs an agent that decides what structures to create and how they should evolve.

We propose \textbf{User as Code} (UaC), which gives that responsibility to the language model. UaC uses the code-generation capabilities of modern LLMs to maintain an executable view of user data and its data model as typed Python. Its two-phase write path first appends facts from each session without overwriting prior evidence, then periodically generates schemas and typed state from a bounded prefix of the accumulated fact serialization. As the user changes, the model can introduce or revise dataclasses and collections rather than fitting every fact into a fixed human-authored ontology. An interpreter can then enumerate typed records for exact aggregation. Textual fact and archive channels remain available for evidence not represented in the bounded code view.

UaC does not claim that Python alone improves reasoning: on clean, already structured inputs, Full Context with a Python REPL matches UaC. The contribution is a persistent write-and-use architecture that converts unstructured conversation into an evolving, code-readable representation and reuses it across later questions. Specifically, we contribute:
\begin{itemize}
\item \textbf{An LLM-generated executable memory view} whose schemas and typed state are generated rather than fixed by a human. The representation supports attribute access, complete-set computation, and deterministic checks against explicit invariants with ordinary Python.
\item \textbf{A durable-source/write-view architecture} that retains append-only facts and raw conversation separately from the generated code view. The three answer-time channels can therefore recover evidence that the bounded structuring input or generated schema omits.
\item \textbf{Evaluation of three memory capabilities:} factual recall across all 1{,}986 LOCOMO annotations in two model panels, complete-set computation on 100 aggregate cases, and delayed activation of 17 constraints spanning four domains.
\end{itemize}

\section{Related Work}
\label{sec:related}

Most agent-memory systems follow a store--retrieve pattern. They store atomic facts (Mem0~\citep{chhikara2025mem0}), linked notes (A-MEM~\citep{xu2025amem}), temporal graphs (Zep/Graphiti~\citep{rasmussen2025zep}), episodes (MemMachine~\citep{wang2026memmachine}), or hybrid logical networks (Hindsight~\citep{latimer2025hindsight}). OS-inspired systems such as MemGPT~\citep{packer2023memgpt} manage text pages through an editable memory hierarchy. UaC instead makes a generated view of persistent user state executable: schemas and instances are LLM-generated Python that evolves with the user.

The closest persistent alternative is LangMem~\citep{langmem2025}, which lets agents revise long-term natural-language instructions. UaC differs by storing typed state that an interpreter can query rather than instructions an LLM must reinterpret at read time. CoCoGen~\citep{madaan2022cocogen} likewise shows that code can improve structured generation, while Code as Policies and VeraFi~\citep{liang2023codeaspolicies,akinfaderin2025verafi} generate executable policies or machine-checkable constraints. Those artifacts are typically task-specific; UaC maintains generated schemas and instances as an evolving user-memory view. Learned memory policies such as Memory-R1 and AgeMem~\citep{yan2025memoryr1,yu2026agemem} optimize operations over memory APIs, a complementary direction that could train UaC's file-level operations.

Generated code has improved arithmetic and logical reasoning in PAL and Program-of-Thoughts~\citep{gao2023pal,chen2023pot}, agent actions in CodeAct~\citep{wang2024codeact}, and reusable skills in Voyager~\citep{wang2024voyager}. Those artifacts generally solve a task or encode a policy; UaC applies their determinism and verifiability to long-lived user state. Existing benchmarks test long-horizon recall~\citep{maharana2024locomo,wu2025longmemeval}; our analytical benchmark complements them with deterministically scored aggregation over collections of user records.


\section{Methodology: The User as Code Architecture}
\label{sec:method}

Extraction (Section~\ref{sec:extraction}) converts raw multi-session conversation into an append-only fact source and a periodically generated typed-code view. Retrieval and use (Section~\ref{sec:retrieval-use}) answers questions through the code, fact, and archive channels. We first show the generated state (Section~\ref{sec:code-example}), then describe the write and read paths; cross-cutting design principles follow in Section~\ref{sec:principles}.

\subsection{Extraction: Memorize, then Structure}
\label{sec:extraction}

The write path separates a durable append-only fact source from a generated typed-code view.

\subsubsection{Phase 1: Memorize (per session, append-only)}

An LLM extracts every individual fact as a flat string from the first 12{,}000 session characters. Facts are appended---never overwritten or deleted---and relative dates are resolved against the session timestamp, as in Figure~\ref{fig:two-phase-example}. This produces roughly 50--75 facts/session; our run extracts 1{,}419 facts from the 19-session \texttt{conv-30}.\footnote{Phase~1 is mildly stochastic; an independent audit run reports 1{,}433 facts.} Each fact receives session/date provenance and a monotonic identifier before cosine indexing with ChromaDB's default embedder. Independently, the raw session is stored in speaker-aligned chunks of at most 300 words with approximately 75 words of overlap. Atomic facts support normalized retrieval; the archive preserves exact wording, and neither is rewritten when the code view changes.

\subsubsection{Phase 2: Structure (periodic, bounded input)}

An LLM generates structured Python from the serialized fact list, organizing the visible facts into typed dataclasses: \texttt{date()} for dates, typed lists for collections, and \texttt{notes: list[str]} for hard-to-type facts. The evaluated Phase~2 implementation truncates that serialization to the first 30{,}000 characters before the structuring call. In LOCOMO, all sessions of one conversation are ingested before this call; a later write marks the code view stale until it is regenerated. Regeneration replaces only the view, never the fact list or archive. Because Phase~2 uses a fixed prefix, facts appearing later in a long history may be absent from the typed view. They remain available through the append-only fact index and raw archive at answer time. Hierarchical or incremental structuring is required to remove this ceiling.

\begin{algorithm}[t]
\caption{Evaluated UaC update and recall path.}
\label{alg:uac}
\begin{algorithmic}[1]
\REQUIRE sessions $S$, timestamps $T$, question $q$
\STATE $F \gets [\,]$; initialize fact index $I_F$ and archive index $I_A$
\FOR{each $(s,t) \in (S,T)$}
  \STATE $I_A.\mathrm{add}(\mathrm{chunk}(s,300,75),t)$
  \STATE $\Delta F \gets \mathrm{ExtractFacts}(s,t)$
  \STATE $F \gets F\,\Vert\,\Delta F$; $I_F.\mathrm{add}(\Delta F,t)$
\ENDFOR
\STATE $x \gets \mathrm{prefix}_{30000}(\mathrm{serialize}(F))$
\STATE $V \gets \mathrm{GenerateTypedPython}(x)$
\STATE $C \gets [\mathrm{prefix}_{6000}(V);\ I_F.\mathrm{top}_{20}(q);\ I_A.\mathrm{top}_{10}(q)]$
\RETURN $\mathrm{AnswerLLM}(q,C)$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:uac} makes the asymmetry explicit: $F$ and $I_A$ are durable sources, while $V$ is a disposable materialized view. Prefix limits bound both the structuring call and the answer prompt, but they do not bound what remains retrievable from the two source indices. This design prevents view regeneration from becoming a destructive memory update; it does not guarantee that generated Python is complete, semantically correct, or safe to execute. A deployment should parse and validate a candidate view before activation and execute it in an isolated interpreter.

\subsection{Retrieval and Use}
\label{sec:retrieval-use}

At answer time, UaC treats the typed state as one source and backs it with the fact and archive indices for coverage. In the analytical benchmark, a Python REPL executes queries over the typed records.

\subsubsection{Multi-Strategy Retrieval}
\label{sec:retrieval}

At query time, retrieval composes three channels rather than picking one. The two vector channels are standard retrieval-augmented generation~\citep{lewis2020rag} over the user's own history; the channel unique to UaC is the structured-code state, which the others backstop. Each channel addresses a different failure mode of the others: the structured-code channel can return a typed object but only for facts the structuring step has captured; the fact-vector channel covers the long tail of facts that did not make it into the typed schema; and the raw-archive channel preserves the exact conversational phrasing for queries that hinge on wording.

\textbf{(1)~Structured code state.} The structured code is included in the answer prompt, truncated to 6{,}000 characters. The agent can read typed dataclass instances without a separate parse step.

\textbf{(2)~Fact-vector retrieval.} A ChromaDB collection over the append-only fact list (one fact per record, $\sim$50 facts/session) is queried by cosine similarity against the question; the top 20 facts are appended. This recovers facts the structuring step compressed away or normalized to a different surface form.

\textbf{(3)~Archive retrieval.} A second ChromaDB collection holds the raw conversation chunked at session granularity; the top 10 chunks by cosine similarity are appended after deduplication on their first 80 characters. Used as a last-resort fallback for direct-quote questions.

The three channels are concatenated under fixed headers (\texttt{[STATE]}, \texttt{[FACTS]}, \texttt{[ARCHIVE]}) and passed to the answer LLM with no reranking; the prompt instructs it to prefer structured state on conflicts. The answer-channel evaluation quantifies their contribution to LOCOMO recall, while the analytical benchmark separately tests code execution over enumerable state. This distinction is important: LOCOMO does not give UaC a Python tool, so its result measures typed code as answer context. The analytical suite gives both UaC and the raw-record FC+REPL control the same computation interface, isolating whether the representation exposes a complete collection that the interpreter can enumerate.

\textbf{End-to-end retrieval example.} For ``When did Jon lose his job as a banker?'', the three channels expose complementary surfaces from Figure~\ref{fig:two-phase-example}: \texttt{STATE} contains \texttt{date(2023,1,19)}, \texttt{FACTS} contains the normalized January~19 statement, and \texttt{ARCHIVE} retains ``lost my job as a banker yesterday'' together with the January~20 timestamp. The answer call receives all three. This is not voting among independent memories: state supplies the typed answer, while facts and archive preserve recoverable evidence when bounded structuring omits or compresses a detail.

\subsection{Design Principles}
\label{sec:principles}

Two cross-cutting principles are evaluated directly in this paper:

\begin{enumerate}
\item \textbf{Durable Sources and a Generated View.} Append-only facts and the raw archive remain available alongside the bounded typed-code view. The answer-channel study in Section~\ref{sec:channel-evaluation} evaluates the three answer-time sources.
\item \textbf{Executable Analytical Representation.} Typed collections can be enumerated with ordinary Python. Section~\ref{sec:analytical} compares that interface with raw-record execution and retrieval-only systems.
\end{enumerate}

Three further principles guide production deployment but are not isolated by the experiments:

\begin{enumerate}
  \setcounter{enumi}{2}
\item \textbf{Modularity by Life Domain.} Memory partitioned into independent domain packages (e.g., \texttt{travel/}, \texttt{health/}, \texttt{finance/}). Limits cross-domain leakage and supports selective loading at scale.
\item \textbf{Progressive Disclosure.} Compact manifest ($\sim$200--300 tokens, always loaded) with on-demand domain loading. Keeps the prompt budget bounded as the user state grows.
\item \textbf{Agent-Native File System.} User project is a directory in the agent's workspace---no custom memory API needed.
\end{enumerate}


\section{Experiments and Evaluation}
\label{sec:experiments}

\subsection{Setup}

\textbf{Full LOCOMO protocol.}\label{sec:full-locomo-protocol} We evaluate all 1{,}986 annotations across 10 LOCOMO conversations~\citep{maharana2024locomo}: 1{,}540 answer-bearing questions (categories 1--4) and 446 adversarial questions (category~5). Each of seven systems is run with the GPT-5.6 Luna and Gemini~3 Flash Preview.

\textbf{Scoring.} Categories 1--4 use LOCOMO's official category-aware token F1 and a binary same-backbone LLM judge~\citep{zheng2023mtbench} that accepts semantically equivalent answers. Category~5 uses the deterministic refusal criterion and is never judged. Judge accuracy supports within-panel comparisons; cross-panel differences also reflect judge calibration. Token F1 and refusal accuracy lack that judge confound.

\textbf{Baselines and other benchmarks.} Full Context receives timestamped raw sessions in chronological order; its LongMemEval path has no explicit character cap. MemMachine~\citep{wang2026memmachine} stores turns verbatim, retrieves 30, and adds three neighbors per side; its analytical variant retrieves 20 records and adds two neighbors. Hindsight~\citep{latimer2025hindsight} requests 2--5 facts per turn and fuses semantic, BM25, graph, and temporal channels. It uses a 30-day temporal scale, a .7 semantic threshold, .6 graph decay for two hops, 30 candidates per channel, top-five semantic and BM25 expansion seeds, RRF $k{=}60$ over 50 candidates, and \texttt{ms-marco-MiniLM-L-6-v2} reranking to 20 facts under 4,000 tokens. EverMemOS~\citep{hu2026evermemos} builds MemCells, MemScenes, and a profile from 8,000-character sessions. It uses the top three scenes, 20 semantic and 20 BM25 cells, a .5 foresight boost, ten final cells with eight facts each, and a 200-fact profile. Hindsight and EverMemOS permit six attempts. Both are same-backbone reimplementations rather than native-stack reproductions.

Mem0~\citep{chhikara2025mem0} 1.0.5 and A-MEM~\citep{xu2025amem} 0.0.1 use their libraries. Full LOCOMO Mem0 uses Chroma with \texttt{all-MiniLM-L6-v2}, the panel LLM, inferred writes, and search limit 100. Analytical Mem0 uses a local 384-dimensional embedder, 20-record batches, and search limit 20. Bare LongMemEval Mem0 inherits \texttt{gpt-4.1-nano-2025-04-14} ($T=.1$, 2,000-token cap, \texttt{top\_p}=.1), 1,536-dimensional \texttt{text-embedding-3-small}, Qdrant at \texttt{/tmp/qdrant}, and API v1.1. Its search limit is 100, with no similarity threshold or reranker. A-MEM uses \texttt{all-MiniLM-L6-v2}, evolution threshold 100 with five neighbors, answer retrieval depth 10, and structured completion at $T=.7$ with a 4,000-token cap and six attempts.

\textbf{Models and software.} Full LOCOMO uses Luna and Gemini~3 Flash Preview through Krill. UaC nominally requests $T=1.0$ and thinking budgets of 8,192 for Phase~1, 16,384 for Phase~2, and 2,048 for answering, with six attempts. Krill omits these controls and uses provider defaults. Direct Google LongMemEval uses Gemini~3 Flash Preview at $T=1.0$, with thinking budgets of 2,048 for answering and 256 for judging, and permits six attempts. The original 99 analytical cases also used direct Google, with thinking budgets of 4,096 for Full Context, 8,192 for structuring, and 2,048 for answering; the corrected item used Krill provider defaults. The channel and modularity runs used direct Google with a 2,048-token answer budget. Other decoding controls are omitted. Recorded local versions are OpenAI SDK 1.97.1, ChromaDB 1.5.7, sentence-transformers 3.4.1, transformers 4.48.3, and PEFT 0.14.0.

\textbf{Run integrity.} For each system, we store one record per original $(\text{conversation},\text{QA index})$ pair, including the prompt, gold answer, prediction, category-specific score, and judge decision. We keep model panels and systems separate and report Table~\ref{tab:locomo} only after checking all fourteen model--system outputs for exact 1{,}986-question coverage, missing or erroneous records, judge fields, and recomputed aggregates.

\textbf{Run counts.} We report one outcome per system--evaluation item rather than averages over independent replicates. We used resumable and repair jobs only to complete each result set; LongMemEval retains its first 200 completed questions, and we reran the corrected analytical item once per system. In the cue-free study, the textual baselines come from the frozen v2.1 run, whereas UaC is a post-evaluation v3 regression on the same 17 cases and rubrics.

\textbf{Randomness.} We use Python seed 42 for the earlier 200-question LongMemEval sample retained in the resumable 500-question runs, seeds $1000(i+1)+N$ for analytical cases of type $i$ and size $N$, seeds $10000+i$ for modularity domain $i$, and \texttt{PYTHONHASHSEED=0} for isolated constraint execution. We did not set decoding seeds for hosted-model calls, so generation and LLM-mediated memory construction are stochastic and exact outputs may differ across reruns.

\textbf{Statistical analysis.} For binary metrics, we report two-sided 95\% Wilson intervals over evaluation items; these do not measure variation across independent model reruns. Paired binary comparisons use exact two-sided McNemar tests over discordant outcomes, with Holm adjustment within each comparison family.

\textbf{Provider-safety handling.} Luna produced one benign Mem0 write refusal and four benign judge-call refusals. For the write, we split the unchanged session into contiguous turn groups and paraphrased only the blocked single turn; for judging, we reframed the task as semantic equivalence and, when needed, substituted domain-neutral book terms. Questions, gold answers, predictions, and token-F1 scoring remained unchanged, and all affected judge decisions were recorded as wrong. Unknown refusals fail validation.

\subsection{Aggregate Inference}
\label{sec:analytical}

Beyond recall, agents may need aggregate inference over user records, such as counts, grouped averages, time-window filters, and trends. These operations are concise over typed objects but can be lossy under top-$k$ retrieval.

Let $D$ be the complete record collection and $D_k\subseteq D$ the subset returned by top-$k$ retrieval. An aggregate has the form
\[
A(q,D)=\operatorname{reduce}\{g_q(r):r\in D,\ P_q(r)\}.
\]
Here, $P_q$ selects records, $g_q$ maps their contributions, and $\operatorname{reduce}$ counts, sums, or averages. Retrieval instead exposes $A(q,D_k)$ and is exact only when omitted records cannot affect the result. An enumerable view lets the interpreter apply the operation to every record.

\textbf{Benchmark construction.} 100 cases over 10 record types (trips, contacts, meals, transactions, sleep, workouts, books, medical visits, meetings, purchases), 10 cases each covering 10 question patterns (count, sum, average, group-by, time-window filter, multi-condition filter, top-$k$, min/max, threshold, trend). Per-case record counts span $N \in \{20, 50, 100, 200, 500\}$. Scoring is deterministic with type-specific normalization: exact integer and collection checks, 1\%/0.01 tolerance for floats, and case-insensitive string containment; no LLM judge is used. One sleep-trend item originally omitted the year even though its gold computation used 2024; we corrected it to ask explicitly about Q1 to Q2 of 2024 and reran that item for all five systems.

\textbf{Systems.} Five systems, identical cases, Gemini~3 Flash throughout: Full~Context (in-head reasoning over raw JSON), Full~Context+REPL (same data plus \texttt{python}/\texttt{read\_file} tools), UaC (records structured into typed Python, exposed via REPL), MemMachine (top-20 sentence retrieval with contextual expansion), Mem0 (flat fact extraction, top-20).

\textbf{Execution protocol.} Because the benchmark inputs are already normalized records rather than conversations, the UaC runner bypasses Phase~1 and directly asks one structuring call to define a \texttt{data} list of typed dataclass instances. It serializes the complete case up to a separate 500{,}000-character analytical cap; no evaluated case exceeds that cap. The generated program is loaded before the question is shown. UaC and FC+REPL share a persistent Python namespace. Each tool call has a 20-second limit, and each run permits at most 15 model--tool turns. Standard output is truncated to 6,000 characters, while file reads are truncated to 80,000. FC+REPL must read and parse an allowlisted JSON file, whereas UaC begins with the generated typed objects.

UaC also retains the original list as \texttt{records\_raw} for recovery from an inconvenient generated schema. All 100 programs load without a recorded pre-execution error. The model queries only typed \texttt{data} in 65 cases, only \texttt{records\_raw} in 21, and both in 14. The result therefore measures an executable interface with typed state as the primary view and raw-record recovery, not typed state alone. FC+REPL shows that once complete raw records are enumerable through the same tool, Python syntax itself provides no accuracy advantage.

\subsection{Modularity and Progressive Disclosure}
\label{sec:modularity}

We compare three loading strategies on 100 single-domain questions across 10 domains of 50 records each. All use Gemini~3 Flash Preview, a 2,048-token thinking budget, a 20-second REPL, and identical data. \emph{Monolithic} uses eight turns and places all 500 records both in the prompt and in \texttt{records\_raw}. \emph{Modular} and \emph{Manifest} use ten turns and the same \texttt{load\_domain(name)} loader; Modular exposes one-line summaries through a REPL \texttt{manifest}, whereas Manifest places them in the system prompt. Thus, only the presentation of routing hints varies.

Modular attains 98.0\% accuracy with 426{,}856 prompt tokens at a cost of \$0.25, compared with 97.0\%, 10{,}155{,}765, and \$3.64 for Monolithic, and 87.0\%, 624{,}922, and \$0.38 for Manifest. At \$0.30/M prompt and \$2.50/M output-plus-thinking tokens, Modular therefore reduces prompt tokens 23.8$\times$ and cost 14.9$\times$. Its 95\% accuracy interval overlaps Monolithic's (93.0--99.4 versus 91.5--99.0), supporting an efficiency but not an accuracy gain. Manifest is 10pp lower because some upfront summaries route the model to the wrong domain. This schema-clean ablation tests read-side organization, not generated domain boundaries.

\section{Discussion and Limitations}

UaC changes the access interface rather than uniformly improving recall: retrieval preserves textual evidence, while executable state supports complete-set computation and persistent constraints. LOCOMO gains also vary by metric.

Four limitations remain. First, Phase~2 reads only the first 30{,}000 serialized-fact characters, leaving typed state incomplete on long histories. Second, generated Python requires parsing, validation, and sandboxing. Although the cue-free extension compiles validated constraints in trusted code, its cases informed the representation and validation rules, so unseen constraints require a newly frozen suite. Third, the aggregate suite begins with schema-clean records and bypasses Phase~1; because UaC retains \texttt{records\_raw}, comparisons with a typed-state-only variant and query-specific code over raw records remain missing. Finally, controlled baselines simplify published stacks, and full LOCOMO uses the answer backbone as within-panel judge; native reproductions and independent full-scale judging remain future work.

\section{Conclusion}

UaC combines textual evidence with enumerable execution, leading LOCOMO baselines and matching raw-record FC+REPL on all 100 aggregate cases. \textbf{AI assistance disclosure.} Generative AI assisted language, code, and formatting; the authors verified the paper.
