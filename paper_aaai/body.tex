\section{Introduction}
\label{sec:intro}

Consider a personalized agent whose memory contains 100 trips accumulated across years of conversation. The user may ask, ``Where did I stay in Paris?'', but also ``How many times have I traveled to Europe?'' or ``How many trips did I take in 2025?'' The first question may be answered from one relevant memory. The latter questions generally require enumerating the complete trip history, filtering it, and counting the matching records: omitting even one trip can change the answer. These examples expose two distinct uses of long-term memory: factual recall and analytical inference over a collection.

Most agent-memory systems store conversations as text, extracted facts, linked notes, or graphs and answer questions through top-$k$ retrieval. This interface is effective when the answer appears in one or a few records, but retrieval is designed to return the most relevant evidence, not to enumerate a complete collection. Once the number of relevant records exceeds $k$, an exact count or aggregate becomes unreliable. Passing the entire history to the model restores access to the records, but incurs growing context cost and still asks the model to parse and count them in-context. Existing long-term-memory benchmarks likewise emphasize query-driven recall~\citep{maharana2024locomo,wu2025longmemeval,hu2025memoryagentbench} rather than complete-set computation.

A conventional structured database addresses the computational problem only after a suitable data model has been provided. For the travel example, a developer might define a \texttt{Trip} table with dates, countries, and regions, after which the desired counts are straightforward. A general personal agent, however, encounters evolving information across travel, health, finance, relationships, and domains not known in advance. Requiring developers to anticipate and maintain a schema for every such domain turns open-ended user memory into an ontology-engineering problem. Although database schemas can be migrated, the system still needs an agent that decides what structures to create and how they should evolve.

We propose \textbf{User as Code} (UaC), which gives that responsibility to the language model. UaC uses the code-generation capabilities of modern LLMs to maintain an executable view of user data and its data model as typed Python. Its two-phase write path first appends facts from each session without overwriting prior evidence, then periodically generates schemas and typed state from a bounded prefix of the accumulated fact serialization. As the user changes, the model can introduce or revise dataclasses and collections rather than fitting every fact into a fixed human-authored ontology. An interpreter can then enumerate typed records for exact aggregation. Textual fact and archive channels remain available for evidence not represented in the bounded code view.

UaC does not claim that Python alone improves reasoning: on clean, already structured inputs, Full Context with a Python REPL matches UaC. The contribution is a persistent write-and-use architecture that converts unstructured conversation into an evolving, code-readable representation and reuses it across later questions. Specifically, we contribute:
\begin{itemize}[leftmargin=*]
\item \textbf{An LLM-generated executable memory view} whose schemas and typed state are generated rather than fixed by a human. The representation supports attribute access, complete-set computation, and deterministic checks against explicit invariants with ordinary Python.
\item \textbf{A durable-source/write-view architecture} that retains append-only facts and raw conversation separately from the generated code view. The three answer-time channels can therefore recover evidence that the bounded structuring input or generated schema omits.
\item \textbf{Evaluation across recall and aggregate inference:} full 1{,}986-question LOCOMO suites and 100 deterministically scored aggregate cases. UaC has the highest observed persistent-system judge accuracy with Luna/Gemini (78.8\%/80.6\%), with metric-dependent token-F1/refusal tradeoffs, and reaches 100\% aggregate accuracy.
\end{itemize}

\section{Related Work}
\label{sec:related}

Most agent-memory systems follow a store--retrieve pattern. They store atomic facts (Mem0~\citep{chhikara2025mem0}), linked notes (A-MEM~\citep{xu2025amem}), temporal graphs (Zep/Graphiti~\citep{rasmussen2025zep}), episodes (MemMachine~\citep{wang2026memmachine}), or hybrid logical networks (Hindsight~\citep{latimer2025hindsight}). OS-inspired systems such as MemGPT~\citep{packer2023memgpt} manage text pages through an editable memory hierarchy. UaC instead makes a generated view of persistent user state executable: schemas and instances are LLM-generated Python that evolves with the user.

The closest persistent alternative is LangMem~\citep{langmem2025}, which lets agents revise long-term natural-language instructions. UaC differs by storing typed state that an interpreter can query rather than instructions an LLM must reinterpret at read time. CoCoGen~\citep{madaan2022cocogen} likewise shows that code can improve structured generation, while Code as Policies and VeraFi~\citep{liang2023codeaspolicies,akinfaderin2025verafi} generate executable policies or machine-checkable constraints. Those artifacts are typically task-specific; UaC maintains generated schemas and instances as an evolving user-memory view. Learned memory policies such as Memory-R1 and AgeMem~\citep{yan2025memoryr1,yu2026agemem} optimize operations over memory APIs, a complementary direction that could train UaC's file-level operations.

Generated code has improved arithmetic and logical reasoning in PAL and Program-of-Thoughts~\citep{gao2023pal,chen2023pot}, agent actions in CodeAct~\citep{wang2024codeact}, and reusable skills in Voyager~\citep{wang2024voyager}. Those artifacts generally solve a task or encode a policy; UaC applies their determinism and verifiability to long-lived user state. Existing benchmarks test long-horizon recall~\citep{maharana2024locomo,wu2025longmemeval}; our analytical benchmark complements them with deterministically scored aggregation over collections of user records.

Figure~\ref{fig:two-phase-example} grounds the two write phases in a real LOCOMO run. Given Jon's statement ``lost my job as a banker yesterday'' on January~20, Phase~1 emits separate provenance-bearing facts and resolves ``yesterday'' to January~19. The append-only facts remain the durable source; generated Python is a replaceable view whose collections and dates an interpreter can enumerate.

\subsection{Extraction: Memorize, then Structure}
\label{sec:extraction}

The write path separates a durable append-only fact source from a generated typed-code view.

\subsubsection{Phase 1: Memorize (per session, append-only)}

An LLM extracts every individual fact as a flat string from each session. Facts are appended---never overwritten or deleted---and relative dates are resolved against the session timestamp, as in Figure~\ref{fig:two-phase-example}. This produces roughly 50--75 facts/session; our run extracts 1{,}419 facts from the 19-session \texttt{conv-30}.\footnote{Phase~1 is mildly stochastic; an independent audit run reports 1{,}433 facts.} Each fact receives session/date provenance and a monotonic identifier before cosine-similarity indexing in ChromaDB. Independently, the raw session is stored in speaker-aligned chunks of at most 300 words with approximately 75 words of overlap. Atomic facts support normalized retrieval; the archive preserves exact wording, and neither is rewritten when the code view changes.

\subsubsection{Phase 2: Structure (periodic, bounded input)}

An LLM generates structured Python from the serialized fact list, organizing the visible facts into typed dataclasses: \texttt{date()} for dates, typed lists for collections, and \texttt{notes: list[str]} for hard-to-type facts. The evaluated \texttt{UserAsCodeV5.structure()} implementation truncates that serialization to the first 30{,}000 characters before the Phase~2 call. In LOCOMO, all sessions of one conversation are ingested before this call; a later write marks the code view stale until it is regenerated. Regeneration replaces only the view, never the fact list or archive. Consequently, the typed code is a bounded prefix-derived view rather than a structure of the complete LOCOMO fact corpus. The append-only fact index and raw archive retain the broader evidence and remain available at answer time. Hierarchical or incremental structuring is required to remove this ceiling.

\begin{algorithm}[t]
\caption{Evaluated UaC update and recall path.}
\label{alg:uac}
\begin{algorithmic}[1]
\REQUIRE sessions $S$, timestamps $T$, question $q$
\STATE $F \gets [\,]$; initialize fact index $I_F$ and archive index $I_A$
\FOR{each $(s,t) \in (S,T)$}
  \STATE $I_A.\mathrm{add}(\mathrm{chunk}(s,300,75),t)$
  \STATE $\Delta F \gets \mathrm{ExtractFacts}(s,t)$
  \STATE $F \gets F\,\Vert\,\Delta F$; $I_F.\mathrm{add}(\Delta F,t)$
\ENDFOR
\STATE $x \gets \mathrm{prefix}_{30000}(\mathrm{serialize}(F))$
\STATE $V \gets \mathrm{GenerateTypedPython}(x)$
\STATE $C \gets [\mathrm{prefix}_{6000}(V);\ I_F.\mathrm{top}_{20}(q);\ I_A.\mathrm{top}_{10}(q)]$
\RETURN $\mathrm{AnswerLLM}(q,C)$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:uac} makes the asymmetry explicit: $F$ and $I_A$ are durable sources, while $V$ is a disposable materialized view. Prefix limits bound both the structuring call and the answer prompt, but they do not bound what remains retrievable from the two source indices. This design prevents view regeneration from becoming a destructive memory update; it does not guarantee that generated Python is complete, semantically correct, or safe to execute. A deployment should parse and validate a candidate view before activation and execute it in an isolated interpreter.

\subsection{Retrieval and Use}
\label{sec:retrieval-use}

At answer time, UaC treats the typed state as one source and backs it with the fact and archive indices for coverage. In the analytical benchmark, a Python REPL executes queries over the typed records.

\subsubsection{Multi-Strategy Retrieval}
\label{sec:retrieval}

At query time, retrieval composes three channels rather than picking one. The two vector channels are standard retrieval-augmented generation~\citep{lewis2020rag} over the user's own history; the channel unique to UaC is the structured-code state, which the others backstop. Each channel addresses a different failure mode of the others: the structured-code channel can return a typed object but only for facts the structuring step has captured; the fact-vector channel covers the long tail of facts that did not make it into the typed schema; and the raw-archive channel preserves the exact conversational phrasing for queries that hinge on wording.

\textbf{(1)~Structured code state.} The structured code is included in the answer prompt, truncated to 6{,}000 characters. The agent can read typed dataclass instances without a separate parse step.

\textbf{(2)~Fact-vector retrieval.} A ChromaDB collection over the append-only fact list (one fact per record, $\sim$50 facts/session) is queried by cosine similarity against the question; the top 20 facts are appended. This recovers facts the structuring step compressed away or normalized to a different surface form.

\textbf{(3)~Archive retrieval.} A second ChromaDB collection holds the raw conversation chunked at session granularity; the top 10 chunks by cosine similarity are appended. Used as a last-resort fallback for direct-quote questions.

The three channels are concatenated under fixed headers (\texttt{[STATE]}, \texttt{[FACTS]}, \texttt{[ARCHIVE]}) and passed to the answer LLM with no reranking; the prompt instructs it to prefer structured state on conflicts. The answer-channel evaluation quantifies their contribution to LOCOMO recall, while the analytical benchmark separately tests code execution over enumerable state. This distinction is important: LOCOMO does not give UaC a Python tool, so its result measures typed code as answer context. The analytical suite gives both UaC and the raw-record FC+REPL control the same computation interface, isolating whether the representation exposes a complete collection that the interpreter can enumerate.

\textbf{End-to-end retrieval example.} For ``When did Jon lose his job as a banker?'', the three channels expose complementary surfaces from Figure~\ref{fig:two-phase-example}: \texttt{STATE} contains \texttt{date(2023,1,19)}, \texttt{FACTS} contains the normalized January~19 statement, and \texttt{ARCHIVE} retains ``lost my job as a banker yesterday'' together with the January~20 timestamp. The answer call receives all three. This is not voting among independent memories: state supplies the typed answer, while facts and archive preserve recoverable evidence when bounded structuring omits or compresses a detail.

\subsection{Design Principles}
\label{sec:principles}

Two cross-cutting principles are evaluated directly in this paper:

\begin{enumerate}[leftmargin=*]
\item \textbf{Durable Sources and a Generated View.} Append-only facts and the raw archive remain available alongside the bounded typed-code view. The answer-channel study in Section~\ref{sec:channel-evaluation} evaluates the three answer-time sources.
\item \textbf{Executable Analytical Representation.} Typed collections can be enumerated with ordinary Python. Section~\ref{sec:analytical} compares that interface with raw-record execution and retrieval-only systems.
\end{enumerate}

Three further principles guide production deployment but are not isolated by the experiments:

\begin{enumerate}[leftmargin=*,start=3]
\item \textbf{Modularity by Life Domain.} Memory partitioned into independent domain packages (e.g., \texttt{travel/}, \texttt{health/}, \texttt{finance/}). Limits cross-domain leakage and supports selective loading at scale.
\item \textbf{Progressive Disclosure.} Compact manifest ($\sim$200--300 tokens, always loaded) with on-demand domain loading. Keeps the prompt budget bounded as the user state grows.
\item \textbf{Agent-Native File System.} User project is a directory in the agent's workspace---no custom memory API needed.
\end{enumerate}


\section{Experiments and Evaluation}
\label{sec:experiments}

\subsection{Setup}

\textbf{Full LOCOMO protocol.}\label{sec:full-locomo-protocol} We evaluate all 1{,}986 annotations across 10 LOCOMO conversations~\citep{maharana2024locomo}: 1{,}540 answer-bearing questions (categories 1--4) and 446 adversarial questions (category~5). Each of seven systems is run with the GPT-5.6 Luna and Gemini~3 Flash Preview.

\textbf{Scoring.} Categories 1--4 use LOCOMO's official category-aware token F1 and a binary same-backbone LLM judge~\citep{zheng2023mtbench} that accepts semantically equivalent answers. Category~5 uses the deterministic refusal criterion and is never judged. Judge accuracy supports within-panel comparisons; cross-panel differences also reflect judge calibration. Token F1 and refusal accuracy lack that judge confound.

\textbf{Baselines and other benchmarks.} Five memory systems are compared with a Full-Context reference. Mem0~\citep{chhikara2025mem0} (mem0ai 1.0.5) and A-MEM~\citep{xu2025amem} (agentic-memory 0.0.1) use their libraries with the selected model API in full LOCOMO. MemMachine~\citep{wang2026memmachine}, Hindsight~\citep{latimer2025hindsight}, and EverMemOS~\citep{hu2026evermemos} are same-backbone reimplementations on shared ChromaDB/\texttt{all-MiniLM-L6-v2}, not native-stack reproductions. LongMemEval uses the Gemini~3 Flash API. The analytical artifacts use Gemini~3 Flash Preview; after correcting one year-ambiguous item, we reran that item for all five systems with the same API before recomputing aggregates.

\textbf{Controlled implementation details.} Full Context receives the timestamped raw sessions in chronological order. MemMachine stores each turn verbatim, retrieves the 30 closest turns, and expands every hit by three neighboring turns on either side. Hindsight extracts typed facts into four logical networks and fuses semantic, BM25, graph, and temporal candidate lists with reciprocal-rank fusion ($k{=}60$), then cross-encoder reranks to 20 facts under a 4{,}000-token context budget. EverMemOS extracts session-level MemCells, consolidates them into MemScenes and a user profile, then combines top-3 scene routing with semantic and BM25 cell retrieval. These implementations preserve the systems' central storage and retrieval mechanisms while replacing their native services with shared local infrastructure; their scores therefore characterize the controlled harness, not the strongest published deployment of each system.

\textbf{Run integrity.} Every system writes one record per original $(\text{conversation},\text{QA index})$ pair, including the prompt, gold answer, prediction, category-specific score, and judge decision. Model panels and systems are stored separately. The paper-facing validator requires exact 1{,}986-question coverage, rejects error records or missing judge fields, recomputes aggregates, and checks all fourteen model--system artifacts before emitting Table~\ref{tab:locomo}.

\textbf{Provider-safety handling.} Luna refused one benign Mem0 write about four dogs/veterinary checkups; only that turn received a documented meaning-preserving paraphrase after session splitting. It also refused four systems' judge calls for one benign book-comparison QA; only the retry prompt used deterministic domain-neutral terms. Stored questions, golds, predictions, and token-F1 paths are unchanged; all four judge decisions are WRONG and artifact-tagged. Unknown refusals fail the build.

\subsection{Aggregate Inference}
\label{sec:analytical}

Beyond recall, agents may need \emph{aggregate inference over the user's records}---``how many contacts did I meet during undergrad'', ``average dining spend in 2024 by cuisine'', or ``did my workout count increase from Q1 to Q2''. Counts, group-bys, time-window filters, and joins are one-line Python over typed objects but can be lossy under top-$k$ retrieval, so this is where code-readable collections should help.

Let $D$ be the complete record collection and $D_k\subseteq D$ the subset returned by top-$k$ retrieval. An aggregate has the form
\[
A(q,D)=\operatorname{reduce}\{g_q(r):r\in D,\ P_q(r)\}.
\]
Retrieval instead exposes $A(q,D_k)$. Counts and sums are exact only when every omitted matching record contributes zero; averages can change in both numerator and denominator. An enumerable view changes the access contract: the interpreter can apply $P_q$ and $g_q$ to every visible record, rather than asking similarity search to predict which records affect the aggregate.

\textbf{Benchmark construction.} 100 cases over 10 record types (trips, contacts, meals, transactions, sleep, workouts, books, medical visits, meetings, purchases), 10 cases each covering 10 question patterns (count, sum, average, group-by, time-window filter, multi-condition filter, top-$k$, min/max, threshold, trend). Per-case record counts span $N \in \{20, 50, 100, 200, 500\}$. Scoring is deterministic with type-specific normalization: exact integer and collection checks, 1\%/0.01 tolerance for floats, and case-insensitive string containment; no LLM judge is used. One sleep-trend item originally omitted the year even though its gold computation used 2024; we corrected it to ask explicitly about Q1 to Q2 of 2024 and reran that item for all five systems.

\textbf{Systems.} Five systems, identical cases, Gemini~3 Flash throughout: Full~Context (in-head reasoning over raw JSON), Full~Context+REPL (same data plus \texttt{python}/\texttt{read\_file} tools), UaC (records structured into typed Python, exposed via REPL), MemMachine (top-20 sentence retrieval with contextual expansion), Mem0 (flat fact extraction, top-20).

\textbf{Execution protocol.} Because the benchmark inputs are already normalized records rather than conversations, the UaC runner bypasses Phase~1 and directly asks one structuring call to define a \texttt{data} list of typed dataclass instances. It serializes the complete case up to a separate 500{,}000-character analytical cap; no evaluated case exceeds that cap. The generated program is loaded before the question is shown. UaC and FC+REPL then share a persistent Python namespace, a 20-second limit per tool call, and at most 15 model--tool turns. FC+REPL must read and parse an allowlisted JSON file, whereas UaC begins with the generated typed objects.

The UaC namespace also retains the original list as \texttt{records\_raw} so a malformed or inconvenient generated schema does not make the case unrecoverable. All 100 generated programs load without a recorded pre-execution error, but the stored tool traces show that the model queries only typed \texttt{data} in 65 cases, only \texttt{records\_raw} in 21, and both in 14. The UaC row therefore evaluates an executable memory interface with typed state as the primary view and raw records as a recovery channel; it is not a dataclass-only lesion. FC+REPL controls for the stronger claim: once complete raw records are enumerable through the same tool, Python syntax itself provides no accuracy advantage. Isolating the incremental effect of typed objects requires a future run that removes UaC's raw fallback.

\subsection{Modularity and Progressive Disclosure}
\label{sec:modularity}

We compare three loading strategies on 100 single-domain questions over a 10-domain, 500-record state. All strategies receive identical records, questions, Python REPL access, and model. \emph{Monolithic} serializes all 500 records into every system prompt and also exposes them as \texttt{records\_raw}. \emph{Modular} initially exposes only the domain names and a \texttt{load\_domain(name)} function, which materializes the chosen 50-record collection. \emph{Manifest} adds a one-line natural-language summary per domain before the same on-demand load. This separates the effect of state partitioning from the routing hint used to select a partition.

Modular loading preserves accuracy while reducing prompt tokens 23.8$\times$ and cost 14.9$\times$ relative to Monolithic. The cost ratio is computed from the unrounded totals (\$3.638797/\$0.2446868), not the two-decimal values displayed in Table~\ref{tab:modularity}. Because the Modular and Monolithic accuracies differ by only one question, this experiment supports efficiency rather than an accuracy advantage. Manifest routing is 10pp below Modular; trace inspection shows that its additional errors arise when a short summary routes the model to the wrong domain. Progressive disclosure is therefore beneficial only when routing remains reliable: loading an explicitly selected domain bounds prompt growth by the largest relevant partition, while a lossy manifest can become a new retrieval bottleneck. As in the analytical suite, the records are schema-clean, so this ablation evaluates read-side organization rather than the quality of LLM-generated domain boundaries.

\section{Discussion and Limitations}

UaC changes the access interface rather than uniformly improving recall. We report LOCOMO token F1, within-panel same-backbone judge accuracy, and adversarial refusal separately; cross-panel judge comparisons also change the judge. The answer-channel evaluation shows that structured state changes conventional QA only slightly, whereas the aggregate benchmark demonstrates the value of an enumerable representation. Retrieval remains complementary: Phase~1 facts preserve normalized atomic evidence, the archive preserves wording and local dialogue, and Phase~2 supplies a disposable computational view. The representation should therefore be read as durable sources plus a generated index, not as a claim that Python replaces textual memory.

Four limitations remain. First, Phase~2 reads only the first 30{,}000 serialized-fact characters, so typed state is incomplete on long LOCOMO histories; hierarchical or incremental structuring is needed. Second, generated Python may be incomplete or semantically wrong and requires parsing, validation, and sandboxing before use. Third, the aggregate suite starts from synthetic, schema-clean records and bypasses Phase~1; UaC also retains \texttt{records\_raw}, so a typed-state-only lesion and a component-pure direct-to-code write-path comparison remain missing. Finally, controlled baselines simplify some published stacks, and the full LOCOMO answer backbone also judges within each panel; a cross-family audit covers only the legacy 600-question subset. Native reproductions and independent full-scale judging remain future work.

\section{Conclusion}

Python rather than Markdown is a functional choice, not a stylistic one. Markdown preserves human-readable evidence, but prose does not by itself expose a typed collection that an interpreter can enumerate. Generated Python makes schemas and records explicit, enabling deterministic filters, counts, joins, and temporal aggregates without reconstructing structure at every query. UaC therefore retains append-only facts and raw conversation for recall while using Python as a replaceable computational view. Executable state also permits deterministic checks against explicit constraints---for example, whether a planned departure occurs after a stored passport expiration date---although reliable proactive constraint monitoring remains future work.

The experiments support this division of labor. UaC achieves the highest observed persistent-system judge accuracy on full LOCOMO in both model panels, with metric-dependent token-F1 and refusal tradeoffs, and remains within 2.4pp of the best system on LongMemEval. In the answer-channel study, facts and archive excerpts provide most of the conventional QA benefit, whereas structured state provides the executable interface. On aggregate inference, UaC+REPL and raw-record FC+REPL both answer all 100 cases correctly at every tested collection size, while retrieval-only systems degrade as the collection grows. Modular loading also preserves accuracy while reducing prompt tokens by 23.8$\times$ and cost by 14.9$\times$, although lossy manifest routing reduces accuracy. Thus, the central advantage is not Python syntax itself, but complete, executable access to user records; Python provides that access in a representation an agent can generate and reuse.
