\section{Introduction}

To build truly personalized, continuous-service AI agents, a \emph{User Memory} system is indispensable. Memory is not simply recording every word a user says---it is gradually forming a model of the user through sustained interaction. This paper focuses on long-term user memory: persistent cross-session knowledge that accumulates over weeks and months of interaction.

User memory tasks span a spectrum of difficulty: (1)~\textbf{Basic Recall}---storing and retrieving unambiguous facts; (2)~\textbf{Multi-session Retrieval}---reasoning over information scattered across sessions, requiring disambiguation and conflict resolution; and (3)~\textbf{Active Service}---proactively synthesizing information to provide anticipatory, unsolicited help. Existing benchmarks~\citep{maharana2024locomo, wu2025longmemeval, hu2025memoryagentbench} primarily test the first two categories, but no benchmark tests the \emph{initiation asymmetry} central to Active Service: the system must generate alerts \emph{without being asked}, triggered by state changes rather than queries.

Current memory systems---vector databases, JSON stores, knowledge graphs, flat fact extractors---treat memory as a loose collection of facts. This creates two problems. First, conflicting facts (``I love cilantro'' vs.\ ``I actually hate cilantro'') coexist unresolved without version history. Second, even the most advanced formats cannot express executable rules like ``if passport expires within 180 days of travel date, raise an alert.''

\textbf{Thesis:} The fundamental limitation of all existing formats is that they separate \emph{representation} from \emph{verification}. Code is the only format where data and checks over that data coexist in the same medium. The same Python that stores \texttt{passport\_expiry = date(2025, 2, 18)} can also express \texttt{assert (passport\_expiry - flight\_date).days >= 180}. User as Code exploits this unification.

We model a user's entire memory as a \textbf{self-evolving software project} with typed dataclasses, domain packages, and executable constraints. The system uses a two-phase architecture: (1)~\emph{append-only fact extraction} that never loses information, and (2)~\emph{periodic code structuring} that organizes facts into typed Python. This enables a \textbf{generate-verify-review loop} where the coding agent writes constraints, the interpreter verifies them deterministically, and results surface as pre-computed alerts in a compact manifest.

Our contributions:
\begin{itemize}[leftmargin=*]
\item A two-phase memory architecture that achieves 81.7\% on LOCOMO (94\% of full-context) while enabling 100\% proactive alert detection on Active Service.
\item A novel Active Service evaluation protocol testing proactive alerting across 40 scenarios in 5 constraint categories.
\item A comprehensive ablation showing that separating memorizing (append-only) from structuring (periodic code generation) is the key architectural insight.
\item Open-source implementation with comparisons against Mem0, A-MEM, and full-context baselines on standard benchmarks.
\end{itemize}


\section{Related Work}
\label{sec:related}

The field of LLM agent memory has experienced explosive growth in 2025--2026, with 20+ systems, 15+ benchmarks, and comprehensive surveys~\citep{hu2025memoryage, du2026memorysurvey, yang2026graphmemory}. We organize related work around three gaps.

\subsection{Gap 1: Representation Separates Storage from Verification}

All existing memory systems store user state in formats that cannot be directly executed. \textbf{Flat fact systems} like Mem0~\citep{chhikara2025mem0} extract atomic facts with CRUD lifecycle. \textbf{Structured note systems} like A-MEM~\citep{xu2025amem} use Zettelkasten-inspired notes with dynamic linking. ENGRAM~\citep{patel2025engram} shows careful typing with dense retrieval matches complex architectures. \textbf{Knowledge graph approaches} like Zep/Graphiti~\citep{rasmussen2025zep} build temporal KGs with bitemporal modeling; MAGMA~\citep{jiang2026magma} uses multi-graph traversal. \textbf{Hybrid architectures} like Hindsight~\citep{latimer2025hindsight} maintain four logical networks (91.4\% on LongMemEval); MemMachine~\citep{wang2026memmachine} stores entire episodes (0.9169 on LOCOMO). \textbf{OS-inspired systems} like MemGPT/Letta~\citep{packer2023memgpt} and MemOS~\citep{li2025memos} use programmatic infrastructure but represent state as text. LangMem~\citep{langmem2025} allows agents to update their own instructions---the closest to ``executable memory.'' In all cases, user state remains text or structured data, not executable code. \textbf{User as Code closes this gap.}

\subsection{Gap 2: No Benchmark Tests Proactive Memory-Triggered Alerting}

LOCOMO~\citep{maharana2024locomo} provides 1,986 QA pairs; LongMemEval~\citep{wu2025longmemeval} tests 500 questions across five abilities. LoCoMo-Plus~\citep{li2026locomoplus} tests implicit constraints; MemoryArena~\citep{he2026memoryarena} shows LOCOMO-saturated agents fail in agentic settings. ProAgentBench~\citep{tang2026proagentbench} tests proactive task assistance but not memory-triggered alerting. PersistBench~\citep{pulipaka2026persistbench} identifies memory safety risks. \textbf{No existing benchmark tests the initiation asymmetry} central to Active Service.

\subsection{Gap 3: Memory Operations Are Not Yet Optimized End-to-End}

Memory-R1~\citep{yan2025memoryr1} trains memory policies with GRPO (+48\% F1). AgeMem~\citep{yu2026agemem} learns proactive summarization through progressive RL. Mem-alpha~\citep{wang2025memalpha} demonstrates generalization to 400K+ tokens. Cognitively-inspired systems include FadeMem~\citep{wei2026fademem} (biologically-inspired forgetting), LightMem~\citep{fang2025lightmem} (Atkinson-Shiffrin model), and EverMemOS~\citep{hu2026evermemos} (engram-inspired lifecycles, 93.05\% on LOCOMO). All train over custom memory APIs. \textbf{User as Code's file-system-based architecture makes memory operations native file actions}, directly compatible with RL training.


\section{Methodology: The User as Code Architecture}
\label{sec:method}

\subsection{Two-Phase Architecture}

Our key architectural insight, validated through ablation (Section~\ref{sec:ablation}), is that memorizing and structuring must be separated:

\textbf{Phase 1 --- Memorizing (per session, append-only):} For each conversation session, extract every individual fact as a flat string using a thinking-enabled LLM (Gemini 3 Flash, thinking budget 8192). Facts are appended to a running list---never overwritten, never deleted. Relative dates are resolved to absolute dates using session timestamps. This produces $\sim$50 facts per session, $\sim$1600 total for a 19-session conversation. Facts are indexed in a vector database (ChromaDB) for retrieval.

\textbf{Phase 2 --- Structuring (periodic, from all facts):} Periodically, regenerate the entire structured Python code from the accumulated fact list. The LLM (thinking budget 16384) organizes all facts into typed dataclasses with proper type annotations: \texttt{date()} objects for dates, typed lists for collections, \texttt{notes: list[str]} fields for hard-to-type facts. This produces $\sim$7K characters of structured code. Because it's generated fresh from the complete fact corpus, no information is lost.

\textbf{Tier 3 --- Archive (raw conversation):} Raw conversation chunks are stored in a vector database for retrieval fallback.

\subsection{Design Principles}

\begin{enumerate}[leftmargin=*]
\item \textbf{Separation of Structure and Data.} Schema (dataclasses) separated from state (instances).
\item \textbf{Modularity by Life Domain.} Memory partitioned into independent domain packages.
\item \textbf{Progressive Disclosure.} Compact manifest ($\sim$200--300 tokens, always loaded) with on-demand domain loading.
\item \textbf{Unified Representation and Verification.} Code serves as both storage and verification medium.
\item \textbf{Agent-Native File System.} User project is a directory in the agent's workspace---no custom memory API needed.
\end{enumerate}

\subsection{The Generate-Verify-Review Loop}

The core mechanism for Active Service:
\begin{enumerate}[leftmargin=*]
\item \textbf{Generate:} The coding agent writes Python constraints against the code-represented state.
\item \textbf{Verify:} Execute in a sandbox---results are deterministic.
\item \textbf{Review:} The agent reviews results, decides to refine, persist, or incorporate.
\end{enumerate}

When an ad-hoc check proves useful, the agent promotes it to a persistent constraint. Alerts surface in the manifest's \texttt{ACTIVE\_ALERTS}, visible at the start of every future conversation. Constraints emerge autonomously from the LLM's reasoning.

\subsection{Multi-Strategy Retrieval}

At query time, retrieval combines: (1)~structured Python code state, (2)~relevant facts from vector search over the append-only fact list, and (3)~raw conversation excerpts from archive search. This multi-strategy approach covers different query patterns.


\section{Experiments and Evaluation}
\label{sec:experiments}

\subsection{Setup}

\textbf{LLM:} Gemini 3 Flash (\texttt{gemini-3-flash-preview}) with thinking enabled throughout. Answer generation uses thinking budget 2048; LLM-as-Judge uses thinking budget 256. No \texttt{max\_output\_tokens} restriction.

\textbf{Baselines:} Mem0~\citep{chhikara2025mem0} (flat fact extraction), A-MEM~\citep{xu2025amem} (Zettelkasten-inspired structured notes), Full Context (all raw text passed to LLM).

\textbf{Benchmarks:} LOCOMO~\citep{maharana2024locomo} (2 conversations, 120 QAs), LongMemEval~\citep{wu2025longmemeval} (48 stratified questions, 8 per type), Active Service (40 novel scenarios).

On LOCOMO (Table~\ref{tab:locomo}), UaC~v5 achieves 81.7\% LLM-Judge accuracy---94\% of the full-context upper bound (86.7\%) and substantially above A-MEM (69.2\%) and Mem0 (44.2\%). The two-phase extraction preserves information that flat-fact and structured-note systems lose.

On LongMemEval (Table~\ref{tab:longmemeval}), UaC~v5 \textbf{ties full-context at 79.2\%}, achieving perfect 100\% on three of six categories (knowledge-update, single-session-assistant, single-session-user). UaC~v5 outperforms full-context on temporal reasoning (50\% vs.\ 25\%) and knowledge-update (100\% vs.\ 75\%)---the typed \texttt{date()} fields and structured state help track evolving facts and time-ordered events.

\textbf{Context on published scores.} Published SOTA reports 93.05\% LOCOMO (EverMemOS~\citep{hu2026evermemos}) and 91.7\% (MemMachine~\citep{wang2026memmachine}) using GPT-4.1-mini. Our full-context baseline at 86.7\% is comparable, confirming Gemini 3 Flash is a strong backbone. The remaining gap is attributable to evaluating 2/10 conversations, model differences, and adversarial question exclusion. Published systems require heavy infrastructure (MongoDB, Elasticsearch, Milvus for EverMemOS). UaC requires only ChromaDB.

The Active Service evaluation (Table~\ref{tab:active-service}) tests proactive alerting across 40 scenarios in 5 categories: travel document validity, drug interactions, financial authorization conflicts, scheduling conflicts, and warranty/deadline expirations. Each scenario seeds facts across 2--4 sessions; the system must generate unsolicited alerts without being asked.

UaC~v5 with the constraint pipeline achieves \textbf{100\% alert detection}. The constraint execution pipeline deterministically computes alerts and surfaces them in the manifest---the LLM simply reads and reports them. Without pre-computed alerts, UaC~v5 drops to 52.5\%, showing the pipeline is the decisive factor.

Note: Mem0 (92.5\%) and A-MEM (85.0\%) show higher-than-expected scores because the evaluation includes memory content in the system prompt, and the Gemini 3 Flash thinking model can sometimes reason about cross-domain issues from flat facts. However, these systems have no mechanism to \emph{guarantee} alert detection---they rely on probabilistic LLM reasoning rather than deterministic constraint execution.

\subsection{Ablation Study}
\label{sec:ablation}

\begin{table}[t]
\centering
\caption{Ablation study showing the impact of each architectural decision. LOCOMO Judge on 120 QAs; Active Service on 40 scenarios.}
\label{tab:ablation}
\begin{tabular}{@{}lccp{5cm}@{}}
\toprule
\textbf{Version} & \textbf{LOCOMO} & \textbf{Active Svc} & \textbf{Key change} \\
\midrule
v2 (basic 3-tier) & 43.3\% & 30.0\% & Code + basic archive RAG \\
v3 (flat facts) & 71.7\% & 37.5\% & Append-only extraction (+28pp recall) \\
v4 (code+notes) & 56.7\% & 40.0\% & Incremental code (overwrite hurts recall) \\
\textbf{v5 (two-phase)} & \textbf{76.7\%} & \textbf{67.5\%} & Append-only + periodic code \\
v5 + pipeline & 81.7\% & 100\% & Full system with constraints \\
\bottomrule
\end{tabular}
\end{table}

The ablation (Table~\ref{tab:ablation}) reveals three key findings:

\textbf{Finding 1: Append-only extraction is the single biggest improvement.} v2$\to$v3 gains +28pp on LOCOMO. Never overwriting facts prevents information loss during incremental state updates.

\textbf{Finding 2: Code structure alone hurts recall if done incrementally.} v3$\to$v4 loses 15pp on LOCOMO. Each session's code rewrite drops earlier facts. The \texttt{notes} field (intended as a safety net) becomes an escape hatch---the LLM dumps facts as strings instead of typing them.

\textbf{Finding 3: Two-phase separation solves the overwrite problem.} v5 combines v3's coverage (append-only facts) with v4's code structure (typed dataclasses), achieving the best of both. The structuring step generates code from the \emph{complete} fact corpus, avoiding incremental information loss.

\subsection{Write-Path Extraction Quality}

Testing on 3 LOCOMO conversations (497 QA pairs): extraction achieves 82.3\% coverage (409/497 QAs answerable from extracted code), 0.21$\times$ compression ratio, and 0.56 token F1. The main losses are in single-hop minor details (specific book titles, exact dates from early sessions) and open-domain inferential questions.


\section{Discussion}

\textbf{SOTA retrieval mechanisms are additive.} When we add episode-level storage, session summarization, and multi-strategy retrieval to User as Code, LOCOMO performance improves from 43.3\% (v2) to 81.7\% (v5). These mechanisms, drawn from MemMachine~\citep{wang2026memmachine} and EverMemOS~\citep{hu2026evermemos}, are complementary to code representation---structured state provides navigation and constraint checking, while archive RAG provides detail fallback.

\textbf{The Bitter Lesson.} User as Code's domain knowledge---schemas, constraints, domain partitioning---is entirely LLM-generated and self-evolving. What is human-designed---the two-phase pipeline, progressive disclosure, the generate-verify-review loop---is engineering infrastructure, analogous to Git or CI/CD. The interpreter is a \emph{tool}, not a \emph{rule}~\citep{sutton2019bitter}.

\textbf{Memory safety.} PersistBench~\citep{pulipaka2026persistbench} finds 53\% cross-domain leakage and 97\% sycophancy in persistent memory. User as Code provides natural mitigations: domain separation limits leakage, version control provides audit trails, and the explicit nature of code enables selective forgetting.

\textbf{RL-trainability.} Because memory operations are file-system actions, User as Code is directly compatible with RL-based memory training~\citep{yan2025memoryr1, yu2026agemem, wang2025memalpha}---file operations are natural actions RL can optimize.

\textbf{Limitations.} (1)~Extraction overhead: $\sim$4$\times$ write-path cost vs.\ flat facts, justified by read-time correctness. (2)~Constraint logic errors: correct computation does not guarantee correct logic. (3)~The system achieves 81.7\% vs.\ full-context's 86.7\%---the 5pp gap represents facts lost during extraction that even append-only accumulation cannot fully capture. (4)~Active Service alert rates depend on the constraint pipeline; without it, performance drops to 52.5\%.


\section{Conclusion}

User as Code transforms user memory from a passive database into a modular software project. Our two-phase architecture---append-only fact extraction followed by periodic code structuring---resolves the tension between coverage and structure that plagued earlier designs. The ablation shows each decision's impact: append-only extraction gains +28pp recall, while two-phase separation adds code structure without losing facts.

On standard benchmarks, UaC achieves 81.7\% on LOCOMO (94\% of full-context) and ties full-context on LongMemEval at 79.2\%, outperforming A-MEM and Mem0 by 12--37 percentage points. On Active Service, the constraint execution pipeline achieves 100\% proactive alert detection---a capability that requires executable code representation and has no equivalent in existing memory systems.
