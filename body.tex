\section{Introduction}

To build truly personalized, continuous-service AI agents, a \emph{User Memory} system is indispensable. Memory is not simply recording every word a user says---it is gradually forming a model of the user through sustained interaction. This paper focuses on long-term user memory: persistent cross-session knowledge that accumulates over weeks and months of interaction.

User memory tasks span a spectrum of difficulty: (1)~\textbf{Basic Recall}---storing and retrieving unambiguous facts; (2)~\textbf{Multi-session Retrieval}---reasoning over information scattered across sessions, requiring disambiguation and conflict resolution; and (3)~\textbf{Active Service}---proactively synthesizing information to provide anticipatory, unsolicited help. Existing benchmarks~\citep{maharana2024locomo, wu2025longmemeval, hu2025memoryagentbench} primarily test the first two categories, but no benchmark tests the \emph{initiation asymmetry} central to Active Service: the system must generate alerts \emph{without being asked}, triggered by state changes rather than queries.

Current memory systems---vector databases, JSON stores, knowledge graphs, flat fact extractors---treat memory as a loose collection of facts. This creates two problems. First, conflicting facts (``I love cilantro'' vs.\ ``I actually hate cilantro'') coexist unresolved without version history. Second, even the most advanced formats cannot express executable rules like ``if passport expires within 180 days of travel date, raise an alert.''

\textbf{Thesis:} The fundamental limitation of free-text and fact-store formats is that they separate \emph{representation} from \emph{verification}. Typed Python unifies the two in the same medium: the same code that stores \texttt{passport\_expiry = date(2025, 2, 18)} can also express \texttt{assert (passport\_expiry - flight\_date).days >= 180}. JSON dicts plus a Python REPL share this property in principle, but require LLM-managed parsing at every query (Section~\ref{sec:analytical}), which becomes unreliable on noisy real-world conversation. User as Code's contribution is the \emph{two-phase pipeline} that converts unstructured conversation into a representation a code tool can read directly.

We model a user's entire memory as a \textbf{self-evolving software project} with typed dataclasses, domain packages, and executable constraints. The system uses a two-phase architecture: (1)~\emph{append-only fact extraction} that never loses information, and (2)~\emph{periodic code structuring} that organizes facts into typed Python. This enables a \textbf{generate-verify-review loop} where the coding agent writes constraints, the interpreter verifies them deterministically, and results surface as pre-computed alerts in a compact manifest.

Our contributions:
\begin{itemize}[leftmargin=*]
\item A two-phase memory architecture that achieves 78.0\% on the 5-conversation LOCOMO subset (300 QAs)---94.7\% of the full-context upper bound (82.3\%) and ahead of three recent SOTA systems reproduced on identical Gemini~3 Flash backbone (MemMachine 75.3\%, Hindsight 70.0\%, EverMemOS 55.0\%)---while enabling 100\% proactive alert detection on Active Service.
\item A novel Active Service evaluation protocol testing proactive alerting across 40 scenarios in 5 constraint categories.
\item \textbf{A new analytical-inference benchmark} (100 cases, 10 record types, $N \in \{20, 50, 100, 200, 500\}$) that exposes the gap between code-executable representations (UaC~v5: 99\%, Full~Context+REPL: 100\%) and retrieval-based ones (MemMachine: 43\%, Mem0: 6\%) on aggregate questions where top-$k$ retrieval is structurally lossy. We also report Gemini~3 Flash token cost per system: UaC~v5's structuring pays for itself after \texttildelow3 queries against the same user state, after which it costs an order of magnitude less than re-loading the records each query.
\item A comprehensive ablation showing that separating memorizing (append-only) from structuring (periodic code generation) is the key architectural insight.
\item A Modularity / Progressive Disclosure ablation showing that loading only the query-relevant domain (rather than the full user state) reduces prompt-token cost by 12--15$\times$ at a 7--17pp accuracy cost, validating the principles for production scale.
\item Cross-LLM portability validated by re-running the full pipeline with GPT-5.4 (OpenAI) replacing Gemini~3 Flash, recovering 80.8\% on the 2-conversation LOCOMO subset (within 2pp of Gemini).
\item Open-source implementation with comparisons against Mem0, A-MEM, MemMachine, and full-context baselines on three benchmarks.
\end{itemize}


\section{Related Work}
\label{sec:related}

The field of LLM agent memory has experienced explosive growth in 2025--2026, with 20+ systems, 15+ benchmarks, and comprehensive surveys~\citep{hu2025memoryage, du2026memorysurvey, yang2026graphmemory}. We organize related work around three gaps.

\subsection{Gap 1: Representation Separates Storage from Verification}

All existing memory systems store user state in formats that cannot be directly executed. \textbf{Flat fact systems} like Mem0~\citep{chhikara2025mem0} extract atomic facts with CRUD lifecycle. \textbf{Structured note systems} like A-MEM~\citep{xu2025amem} use Zettelkasten-inspired notes with dynamic linking. ENGRAM~\citep{patel2025engram} shows careful typing with dense retrieval matches complex architectures. \textbf{Knowledge graph approaches} like Zep/Graphiti~\citep{rasmussen2025zep} build temporal KGs with bitemporal modeling; MAGMA~\citep{jiang2026magma} uses multi-graph traversal. \textbf{Hybrid architectures} like Hindsight~\citep{latimer2025hindsight} maintain four logical networks (91.4\% on LongMemEval); MemMachine~\citep{wang2026memmachine} stores entire episodes (0.9169 on LOCOMO). \textbf{OS-inspired systems} like MemGPT/Letta~\citep{packer2023memgpt} and MemOS~\citep{li2025memos} use programmatic infrastructure but represent state as text. LangMem~\citep{langmem2025} allows agents to update their own instructions---the closest to ``executable memory.'' In all cases, user state remains text or structured data, not executable code. \textbf{User as Code closes this gap.}

\subsection{Gap 2: No Benchmark Tests Proactive Memory-Triggered Alerting}

LOCOMO~\citep{maharana2024locomo} provides 1,986 QA pairs; LongMemEval~\citep{wu2025longmemeval} tests 500 questions across six question types. LoCoMo-Plus~\citep{li2026locomoplus} tests implicit constraints; MemoryArena~\citep{he2026memoryarena} shows LOCOMO-saturated agents fail in agentic settings. ProAgentBench~\citep{tang2026proagentbench} tests proactive task assistance but not memory-triggered alerting. PersistBench~\citep{pulipaka2026persistbench} identifies memory safety risks. \textbf{No existing benchmark tests the initiation asymmetry} central to Active Service.

\subsection{Gap 3: Memory Operations Are Not Yet Optimized End-to-End}

Memory-R1~\citep{yan2025memoryr1} trains memory policies with GRPO (+48\% F1). AgeMem~\citep{yu2026agemem} learns proactive summarization through progressive RL. Mem-alpha~\citep{wang2025memalpha} demonstrates generalization to 400K+ tokens. Cognitively-inspired systems include FadeMem~\citep{wei2026fademem} (biologically-inspired forgetting), LightMem~\citep{fang2025lightmem} (Atkinson-Shiffrin model), and EverMemOS~\citep{hu2026evermemos} (engram-inspired lifecycles, 93.05\% on LOCOMO). All train over custom memory APIs. \textbf{User as Code's file-system-based architecture makes memory operations native file actions}, directly compatible with RL training.

\subsection{Two-Phase Architecture}

Our key architectural insight, validated through ablation (Section~\ref{sec:ablation}), is that memorizing and structuring must be separated:

\textbf{Phase 1 --- Memorizing (per session, append-only):} For each conversation session, extract every individual fact as a flat string using a thinking-enabled LLM (Gemini 3 Flash, thinking budget 8192). Facts are appended to a running list---never overwritten, never deleted. Relative dates are resolved to absolute dates using session timestamps. This produces $\sim$50 facts per session, $\sim$950 total for a 19-session conversation. Facts are indexed in a vector database (ChromaDB) for retrieval.

\textbf{Phase 2 --- Structuring (periodic, from all facts):} Periodically, regenerate the entire structured Python code from the accumulated fact list. The LLM organizes all facts into typed dataclasses with proper type annotations: \texttt{date()} objects for dates, typed lists for collections, \texttt{notes: list[str]} fields for hard-to-type facts. The code size scales with the number of distinct facts: a 19-session LOCOMO conversation yields $\sim$7K characters of structured code (thinking budget 16,384), while the analytical-inference benchmark at $N{=}500$ records produces 50K--55K characters (thinking budget 8,192, no record truncation up to 500K input characters). Because the code is generated fresh from the complete fact corpus rather than incrementally, no information is lost during the transition between fact and structure.

\textbf{Archive (raw conversation).} Additionally, raw conversation chunks are stored in a vector database as a retrieval fallback when structured code and extracted facts lack sufficient detail.

\subsection{Design Principles}

Two principles are evaluated directly in this paper:

\begin{enumerate}[leftmargin=*]
\item \textbf{Separation of Structure and Data.} Schema (dataclasses) separated from state (instances). Validated by the v3$\to$v5 ablation (Section~\ref{sec:ablation}).
\item \textbf{Unified Representation and Verification.} Code serves as both storage and verification medium. Validated by Active Service (Section~\ref{sec:active-service}) and Analytical Inference (Section~\ref{sec:analytical}).
\end{enumerate}

Three further principles guide production deployment but are not isolated by the experiments:

\begin{enumerate}[leftmargin=*,start=3]
\item \textbf{Modularity by Life Domain.} Memory partitioned into independent domain packages (e.g., \texttt{travel/}, \texttt{health/}, \texttt{finance/}). Limits cross-domain leakage and supports selective loading at scale.
\item \textbf{Progressive Disclosure.} Compact manifest ($\sim$200--300 tokens, always loaded) with on-demand domain loading. Keeps the prompt budget bounded as the user state grows.
\item \textbf{Agent-Native File System.} User project is a directory in the agent's workspace---no custom memory API needed.
\end{enumerate}

\subsection{The Generate-Verify-Review Loop}

The core mechanism for Active Service:
\begin{enumerate}[leftmargin=*]
\item \textbf{Generate:} The coding agent writes Python constraints against the code-represented state.
\item \textbf{Verify:} Execute in a sandbox---results are deterministic.
\item \textbf{Review:} The agent reviews results, decides to refine, persist, or incorporate.
\end{enumerate}

When an ad-hoc check proves useful, the agent promotes it to a persistent constraint. Alerts surface in the manifest's \texttt{ACTIVE\_ALERTS}, visible at the start of every future conversation. Constraints emerge autonomously from the LLM's reasoning.

\subsection{Multi-Strategy Retrieval}

At query time, retrieval combines: (1)~structured Python code state, (2)~relevant facts from vector search over the append-only fact list, and (3)~raw conversation excerpts from archive search. This multi-strategy approach covers different query patterns.


\section{Experiments and Evaluation}
\label{sec:experiments}

\subsection{Setup}

\textbf{LLM:} Gemini 3 Flash (\texttt{gemini-3-flash-preview}) with thinking enabled throughout. Answer generation uses thinking budget 2048. No \texttt{max\_output\_tokens} restriction.

\textbf{Evaluation:} LLM-as-Judge with binary correctness scoring (CORRECT/WRONG, thinking budget 256). The judge receives the question, gold answer, and prediction, and is instructed to be generous: answers conveying the same core information with different wording or format score CORRECT; answers score WRONG only when factually incorrect or claiming unavailability when the gold answer exists.

\textbf{Baselines:} Mem0~\citep{chhikara2025mem0} (flat fact extraction, mem0ai 1.0.5), A-MEM~\citep{xu2025amem} (Zettelkasten-inspired structured notes), Full Context (all raw text passed to LLM).

\textbf{Benchmarks:} \emph{All four memory systems are evaluated on the same data}: LOCOMO~\citep{maharana2024locomo} (5 conversations, 60 QAs each, 300 QAs total; conv-26, conv-30, conv-41, conv-42, conv-43); LongMemEval~\citep{wu2025longmemeval} (200 stratified questions, 40\% of the 500-question split, seed 42, with type distribution preserved: 54~temporal-reasoning, 53~multi-session, 31~knowledge-update, 28~single-session-user, 22~single-session-assistant, 12~single-session-preference); Active Service (40 standard + 20 hard scenarios).

\textbf{Cross-LLM portability.} To verify that User as Code's gains do not depend on a particular LLM's code-generation idiosyncrasies, we additionally re-run UaC~v5 with GPT-5.4 (OpenAI) replacing Gemini~3 Flash for fact extraction, code structuring, and answer generation. The Gemini~3 Flash judge is reused for fair scoring against the Gemini run. Cross-LLM evaluation uses the 2-conversation LOCOMO subset (120 QAs) for tractability.

On LOCOMO (Table~\ref{tab:locomo}), all four systems are evaluated symmetrically on the same 5-conversation, 300-QA subset. UaC~v5 reaches \textbf{78.0\%}, recovering 94.7\% of the Full Context upper bound (82.3\%) while operating on extracted memory rather than the full transcripts; A-MEM (56.7\%) and Mem0 (32.7\%) lose 21--45pp on the same data. Inspection of the per-question failures shows Mem0's gap is dominated by temporal questions where its extracted memories preserve relative-date references (``yesterday'', ``last week'') without resolving them, and A-MEM's gap is dominated by single-hop detail questions where note-level retrieval surfaces only context summaries rather than the underlying turn content.

On LongMemEval (Table~\ref{tab:longmemeval}), the 200-question stratified sample (4$\times$ larger than the 48-question split used in earlier drafts) shrinks per-category variance and confirms the same ranking. UaC~v5 reaches \textbf{84.5\%}, within 2pp of Full Context (86.5\%), while A-MEM (58.0\%) and Mem0 (24.5\%) trail by 25--60pp. The typed \texttt{date()} fields help on knowledge-update (96.8\%~vs.~90.3\% for Full Context); the gap to Full Context is concentrated in temporal-reasoning (70.4\%~vs.~81.5\%), where the extraction step occasionally drops the timestamps required for date arithmetic over many sessions.

\textbf{Cross-LLM portability.} Replacing Gemini~3 Flash with GPT-5.4 throughout the UaC~v5 pipeline (extraction, structuring, answer generation) recovers \textbf{80.8\%} on the 2-conversation LOCOMO subset (120 QAs)---within 2pp of the Gemini run on the same subset (82.5\%). The architecture is portable across the two largest closed-model families, and the gains are not dependent on a particular LLM's code-generation idiosyncrasies.

\textbf{Comparison to recent SOTA systems.} We reproduce three recent SOTA systems---MemMachine~\citep{wang2026memmachine}, EverMemOS~\citep{hu2026evermemos}, and Hindsight~\citep{latimer2025hindsight}---on the \emph{same} 5-conversation LOCOMO subset and 200-question LongMemEval sample with the \emph{same} Gemini~3 Flash backbone, so any difference reflects representation rather than model. Our reimplementations follow the architectures described in each paper but use approximate prompts (the originals are not always published) and lighter infrastructure (ChromaDB rather than MongoDB+Elasticsearch+Milvus). On LOCOMO (Table~\ref{tab:locomo}): MemMachine reaches 75.3\%, Hindsight 70.0\%, EverMemOS 55.0\%---all behind UaC~v5's 78.0\%. On LongMemEval: EverMemOS 79.5\%, Hindsight 70.5\%---both behind UaC~v5's 84.5\%. The original papers report higher numbers (EverMemOS 93.05\% LOCOMO with GPT-4.1-mini; Hindsight 91.4\% LongMemEval with a Gemini-3 backbone in their full pipeline), but those settings differ in either the LLM, the retrieval stack, or both. Our backbone-controlled comparison shows that User as Code's representational advantage holds against the architectural ideas these systems contribute---structured Python state outperforms episode storage with contextualized retrieval (MemMachine), engram-inspired MemCell/MemScene clusters (EverMemOS), and four-network fact graphs with multi-channel retrieval (Hindsight) under the same model.

\subsection{Analytical Inference}
\label{sec:analytical}

A third capability tier sits between basic recall and proactive alerting: \emph{aggregate inference over the user's records}---answering questions like ``how many contacts did I meet during undergrad'', ``average dining spend in 2024 by cuisine'', or ``did my workout count increase from Q1 to Q2''. This is exactly the regime where a code-executable representation should pull ahead of free-text retrieval: counts, group-bys, time-window filters, and joins are one-line Python over typed objects but fundamentally lossy under top-$k$ retrieval.

\textbf{Benchmark construction.} We synthesize 100 cases spanning 10 record types (trips, contacts, meals, transactions, sleep log, workouts, books, medical visits, work meetings, purchases). Each type contributes 10 cases covering 10 question patterns (count, sum, average, group-by, time-window filter, multi-condition filter, top-$k$, min/max, threshold, year-over-year trend). Per-case record counts span $N \in \{20, 50, 100, 200, 500\}$ to surface scaling behavior. Ground truth is computed deterministically from the synthetic data, so scoring is exact-match (no LLM judge needed).

\textbf{Systems.} Five systems run on identical cases with Gemini~3 Flash backbone: Full Context (LLM in-head reasoning over raw JSON), Full Context + Python REPL (same data, plus \texttt{python} and \texttt{read\_file} tools so the LLM can compute), UaC~v5 (records structured into typed Python dataclasses, exposed via REPL), MemMachine~\citep{wang2026memmachine} (sentence-level retrieval with contextual expansion), and Mem0 (flat fact extraction). Mem0 and MemMachine retrieve top-20 entries and have the LLM reason over them.

The results (Table~\ref{tab:analytical} and Figure~\ref{fig:analytical-scaling}) split cleanly by representation class. \textbf{Retrieval-based memory collapses on aggregation}: MemMachine drops from 100\% at $N{=}20$ to 15\% at $N{=}200$ as more records become relevant than top-$k$ can return; Mem0 sits near zero throughout because its NL fact stores cannot be enumerated. \textbf{Full Context degrades when $N$ exceeds in-head capacity}: 100\% accuracy through $N{=}100$, dropping to 90\% at $N{=}200$ and $N{=}500$ as the LLM miscounts. \textbf{Adding a Python REPL solves counting completely} (FC+REPL: 100\% overall, perfect across all $N$). \textbf{UaC~v5 matches FC+REPL across the full $N$ range} (overall 99\%, perfect on $N \leq 200$, 95\% at $N{=}500$). The single $N{=}500$ failure is a corner case where Q1 and Q2 averages differ by 0.0012 hours of sleep duration---essentially a tie that the gold rule resolves as ``increase'' but is below the noise floor of the structured Python rounding.

The headline message is the divide between \emph{representations a code tool can read} (UaC~v5, FC+REPL, Full Context for small $N$) and \emph{representations only retrievable by similarity} (Mem0, MemMachine). The former scale with N; the latter do not. UaC~v5's specific advantage---typed objects enabling typed queries---matches a JSON+REPL baseline on this benchmark, because the analytical inputs are already structured. The contribution of UaC's two-phase pipeline is felt earlier: it converts unstructured conversation into the kind of representation a code tool can reason over, which is the prerequisite for analytical inference in real deployments.

\subsubsection{Token cost and amortization}

We additionally instrumented every Gemini call with token counts and computed approximate USD cost using Gemini~3 Flash pricing (Table~\ref{tab:analytical-cost}). Three findings:

\textbf{(1)~On a single-query workload, FC+REPL is both more accurate and cheaper than UaC~v5}: \$13.6 vs \$38.1 per~100 cases (2.8$\times$). UaC's cost is dominated by the structuring step, which generates \texttildelow1M output tokens of dataclass code across 100 cases. FC+REPL's cost is dominated by re-including the records JSON in the LLM context every tool turn (4.2M input tokens).

\textbf{(2)~The cost story flips on multi-query workloads.} Structuring is paid once per user state; subsequent queries against the typed code cost only \texttildelow1.4 m\$/case (Table~\ref{tab:analytical-cost-amortized}). FC+REPL pays the full per-case cost \emph{every} query because it re-loads the records each time. With per-case structuring at ${C_s}$ and per-query costs $q_{\text{UaC}}$ and $q_{\text{FC+REPL}}$, $K$ queries against the same user state cost $C_s + K\,q_{\text{UaC}}$ vs $K\,q_{\text{FC+REPL}}$. At $N{=}500$, $C_s{\approx}102$~m\$, $q_{\text{UaC}}{\approx}1.4$~m\$, $q_{\text{FC+REPL}}{\approx}38$~m\$; UaC pays back its structuring cost after $K \approx 3$ queries, and at $K{=}100$ queries it costs 12$\times$ less than FC+REPL ($244$~m\$ vs $3{,}780$~m\$).

The Active Service evaluation (Table~\ref{tab:active-service}) tests proactive alerting across 40 scenarios in 5 categories: travel document validity, drug interactions, financial authorization conflicts, scheduling conflicts, and warranty/deadline expirations. Each scenario seeds facts across 2--4 sessions; the system must generate unsolicited alerts without being asked. The Mem0 and A-MEM baselines in this table are \emph{hand-crafted flat-fact representations} of each scenario---a simulated upper bound for what those systems' extracted memories would look like---not the live libraries. As a sanity check we additionally ran the actual mem0ai~1.0.5 library on the same scenarios: 90.0\% on standard (close to the 92.5\% simulation) and 80.0\% on hard (higher than the 65.0\% simulation, since the live library returns the full memory list to the LLM rather than top-$k$ facts). Both numbers are below UaC~v5's 100\% standard / 85\% hard, confirming the simulation-based comparison is fair.

UaC~v5 with the constraint pipeline achieves \textbf{100\% alert detection} on the standard scenarios. Without pre-computed alerts, UaC~v5 drops to 52.5\%, showing the pipeline is the decisive factor.

On standard scenarios, Mem0 (92.5\%) and A-MEM (85.0\%) score well because Gemini 3 Flash can reason about simple cross-domain issues from flat facts. To test whether this holds for harder problems, we design 20 \textbf{hard scenarios} requiring multi-step date arithmetic (business day calculations, leap years, timezone crossings), compound multi-domain constraints (4--5 domains), precise numerical thresholds (tax brackets, compound interest, DTI ratios), and temporally ambiguous facts.

The ablation (Table~\ref{tab:ablation}) reveals three key findings:

\textbf{Finding 1: Append-only extraction is the single biggest improvement.} v2$\to$v3 gains +19.0pp on LOCOMO. Never overwriting facts prevents information loss during incremental state updates.

\textbf{Finding 2: Code structure alone hurts recall if done incrementally.} v3$\to$v4 loses 10.0pp on LOCOMO. Each session's code rewrite drops earlier facts. The \texttt{notes} field (intended as a safety net) becomes an escape hatch---the LLM dumps facts as strings instead of typing them.

\textbf{Finding 3: Two-phase separation solves the overwrite problem.} v5 combines v3's coverage (append-only facts) with v4's code structure (typed dataclasses), gaining +12.3pp over v4 and +2.3pp over v3. The structuring step generates code from the \emph{complete} fact corpus, avoiding incremental information loss.

\textbf{Finding 4: The constraint pipeline is orthogonal to LOCOMO QA.} Adding the constraint-generation pipeline on top of v5 leaves LOCOMO QA accuracy unchanged at 78.0\% but lifts Active Service alert detection from 67.5\% to 100\%. The pipeline is a separate read-time mechanism that operates over the same structured state; it does not affect retrieval quality.

\subsection{Modularity and Progressive Disclosure}
\label{sec:modularity}

We finally evaluate two design principles introduced in Section~\ref{sec:method} that the standard benchmarks do not isolate: \emph{Modularity by Life Domain} and \emph{Progressive Disclosure}. We synthesize a multi-domain user state with 6 domains (trips, meals, transactions, contacts, books, sleep) at 50 records each (300 total), then ask 30 single-domain questions (5 per domain, drawn from the analytical benchmark's question patterns). Three loading strategies share the same Python REPL backend and Gemini~3 Flash model:

\textbf{Monolithic:} the full 300-record state is inlined into the LLM system prompt every query (the naive ``always-dump'' baseline).

\textbf{Modular:} only a list of available domain names is in the system prompt. The LLM calls a \texttt{load\_domain(name)} REPL helper to materialize the specific domain it needs.

\textbf{Manifest+routing:} the system prompt additionally contains a one-line summary per domain ($\sim$50 tokens each); the LLM uses the manifest to route then calls \texttt{load\_domain}.

The results (Table~\ref{tab:modularity}, Figure~\ref{fig:modularity}) show what the design principles are buying. Modular loading reduces total prompt tokens by 14.9$\times$ (1.89M $\rightarrow$ 0.13M) at a 6.7pp accuracy cost; the manifest variant is similar in cost but loses an additional 10pp accuracy because the LLM occasionally mis-routes from the brief summaries. The monolithic baseline is perfect on accuracy but pays the full state token cost on every query. In real deployments where a user's state grows to thousands of records and queries happen continuously, the modular pattern is the only one that remains tractable: monolithic cost scales linearly with state size, while modular cost is bounded by the largest single domain.

This ablation confirms that the Modularity and Progressive Disclosure principles are not free lunches---they trade a small accuracy hit for a large cost reduction---but the trade is favorable in any setting where state size makes monolithic prompting unaffordable.


\section{Discussion}

\textbf{SOTA retrieval mechanisms are additive.} The ablation (Table~\ref{tab:ablation}) shows the v2$\to$v5 progression on LOCOMO. Episode-level storage, session summarization, and multi-strategy retrieval (mechanisms drawn from MemMachine~\citep{wang2026memmachine} and EverMemOS~\citep{hu2026evermemos}) are complementary to code representation: structured state provides navigation and constraint checking, while archive RAG provides detail fallback.

\textbf{Domain knowledge is LLM-generated, infrastructure is human-designed.} Schemas, constraints, and domain partitioning are all produced by the LLM at write time and evolve with the user. What is human-designed is engineering infrastructure: the two-phase pipeline, the generate-verify-review loop, and the sandbox boundary. The interpreter is a \emph{tool} that the LLM uses, not a \emph{rule} the LLM must obey~\citep{sutton2019bitter}.

\textbf{Memory safety.} PersistBench~\citep{pulipaka2026persistbench} finds 53\% cross-domain leakage and 97\% sycophancy in persistent memory. User as Code provides natural mitigations: domain separation limits leakage, version control provides audit trails, and the explicit nature of code enables selective forgetting.

\textbf{RL-trainability.} Because memory operations are file-system actions, User as Code is directly compatible with RL-based memory training~\citep{yan2025memoryr1, yu2026agemem, wang2025memalpha}---file operations are natural actions RL can optimize.

\textbf{Limitations.} (1)~Extraction overhead: $\sim$4$\times$ write-path cost vs.\ flat facts, justified by read-time correctness. (2)~Constraint logic errors: correct computation does not guarantee correct logic. (3)~On LOCOMO, UaC~v5 trails Full Context by 4.3pp (78.0\% vs.\ 82.3\%); inspection of failures shows the gap is dominated by single-hop minor details (specific book titles, exact early-session dates) that the extraction step occasionally compresses away. (4)~Active Service alert rates depend on the constraint pipeline; without it, performance drops to 52.5\%. (5)~Scalability of structuring: Phase~2 regenerates the entire structured code from the complete fact corpus; at hundreds of sessions, this may require incremental or hierarchical structuring strategies. (6)~The analytical benchmark uses synthetic, schema-clean records; real-world deployments will have noisier, partially-typed data, which we expect to favor UaC~v5 over the Full~Context+REPL baseline (since the baseline's parsing fragility scales with data noise). (7)~The benchmark's single-query-per-case design favors FC+REPL on cost; the amortization analysis (Section~\ref{sec:analytical}) shows UaC's structuring pays back after \texttildelow3 queries against the same user state. (8)~Cross-LLM portability is verified on Gemini~3 Flash and GPT-5.4, but smaller code generators (e.g., 7--8B parameter models) may produce lower-quality structured code. (9)~Storing user state as executable code requires sandboxed execution and strict isolation to prevent cross-user leakage or code injection.


\section{Conclusion}

User as Code transforms user memory from a passive database into a modular software project. Our two-phase architecture---append-only fact extraction followed by periodic code structuring---resolves the tension between coverage and structure that plagued earlier designs. The ablation shows each decision's impact: append-only extraction gains +19pp recall, while two-phase separation adds code structure without losing facts.

On standard benchmarks evaluated symmetrically across all four systems on the same 5-conversation LOCOMO subset (300 QAs) and 200-question LongMemEval sample, UaC achieves 78.0\% on LOCOMO (94.7\% of the full-context upper bound at 82.3\%) and 84.5\% on LongMemEval (within 2pp of full-context's 86.5\%), outperforming A-MEM (56.7\%/58.0\%) and Mem0 (32.7\%/24.5\%) by 21--60 percentage points. Replacing Gemini~3 Flash with GPT-5.4 throughout the pipeline preserves performance (80.8\% on the 2-conversation LOCOMO subset, within 2pp of the Gemini run). On Active Service, the constraint execution pipeline achieves 100\% proactive alert detection---a capability that requires executable code representation and has no equivalent in existing memory systems.
