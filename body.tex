\section{Introduction}
\label{sec:intro}

To build truly personalized, continuous-service AI agents, a \emph{User Memory} system is indispensable. Memory is not simply recording every word a user says---it is gradually forming a model of the user through sustained interaction. This paper focuses on long-term user memory: persistent cross-session knowledge that accumulates over weeks and months of interaction.

User memory tasks span a spectrum of difficulty: (1)~\textbf{Basic Recall}---storing and retrieving unambiguous facts; (2)~\textbf{Multi-session Retrieval}---reasoning over information scattered across sessions, requiring disambiguation and conflict resolution; and (3)~\textbf{Active Service}---proactively synthesizing information to provide anticipatory, unsolicited help. Existing benchmarks~\citep{maharana2024locomo, wu2025longmemeval, hu2025memoryagentbench} primarily test the first two categories, but no benchmark tests the \emph{initiation asymmetry} central to Active Service: the system must generate alerts \emph{without being asked}, triggered by state changes rather than queries.

Current memory systems---vector databases, JSON stores, knowledge graphs, flat fact extractors---treat memory as a loose collection of facts. This creates two problems. First, conflicting facts (``I love cilantro'' vs.\ ``I actually hate cilantro'') coexist unresolved without version history. Second, even the most advanced formats cannot express executable rules like ``if passport expires within 180 days of travel date, raise an alert.''

\textbf{Thesis:} The fundamental limitation of free-text and fact-store formats is that they separate \emph{representation} from \emph{verification}. Any representation a Python interpreter can read directly---typed objects, JSON dicts, even strings with a parser---collapses the two, the same way that \texttt{passport.expiry\_date = date(2025, 2, 18)} can be stored \emph{and} compared in one medium (see Listings~\ref{lst:travel-state}--\ref{lst:constraint}). Our analytical benchmark confirms this: a Full~Context~+~Python~REPL baseline with the records as raw JSON matches UaC on aggregate queries (Section~\ref{sec:analytical}), so ``code-as-representation'' is not by itself a novel claim. \emph{The contribution of User as Code is the two-phase pipeline that converts unstructured conversation into a representation a code tool can read directly}---without that, every aggregate query pays LLM-managed parsing cost over noisy real-world dialogue. The pipeline shape itself (append-only log + periodic checkpoint) borrows from database systems; the novelty is in applying it to LLM memory, with typed Python as the checkpoint medium.

\textbf{Three things you can do once memory is code.} Listing~\ref{lst:tiers} shows the three capability tiers UaC unlocks, all against the same tiny typed state and all expressible as one-line Python. (a)~\textbf{Recall} is attribute access. (b)~\textbf{Analytical inference} is a list comprehension---trivial in Python, structurally lossy under top-$k$ retrieval (this is the gap quantified in Section~\ref{sec:analytical}: UaC~v5 99\% vs.\ MemMachine 43\%). (c)~\textbf{Active service} is a boolean check over typed dates---one comparison the interpreter runs deterministically at every state change. Figures~\ref{fig:teaser-input}--\ref{fig:teaser-check} then expand (c) into a full life-safety walkthrough where the relevant facts arrive in two conversations ten months apart.

Concretely, we model the user's memory as a self-evolving software project with typed dataclasses, domain packages, and executable constraints. The system uses a two-phase architecture---append-only fact extraction that never loses information, and periodic code structuring that organizes facts into typed Python---which together enable a generate-verify-review loop: the coding agent writes constraints, the interpreter verifies them deterministically, and results surface as pre-computed alerts in a compact manifest. Our contributions:
\begin{itemize}[leftmargin=*]
\item A two-phase memory architecture that achieves 78.8\% on the full 10-conversation LOCOMO benchmark (600 QAs)---within 1.0pp of the full-context upper bound (79.8\%; gap not significant under McNemar, $p{=}0.65$) and ahead of three recent SOTA systems---MemMachine 72.7\%, Hindsight 69.7\%, EverMemOS 55.5\% (all $p<0.005$ under McNemar)---when those systems are reproduced as minimal-faithful, same-backbone (Gemini~3 Flash + ChromaDB) variants of our own (full fidelity statement, Appendix~\ref{app:reimpl}; we treat the published 91--93\% numbers obtained with stronger backbones and multi-service retrieval stacks as ceilings, not direct competitors). The same UaC architecture reaches 100\% proactive alert detection on the 40 standard Active Service scenarios (85\% on the 20 hard scenarios).
\item A novel Active Service evaluation protocol testing proactive alerting across 40 scenarios in 5 constraint categories.
\item \textbf{A new analytical-inference benchmark} (100 cases, 10 record types, $N{\in}\{20, 50, 100, 200, 500\}$ records) that exposes the gap between code-executable representations (UaC~v5: 99\%, Full Context~+~REPL: 100\%) and retrieval-based ones (MemMachine: 43\%, Mem0: 6\%) on aggregate questions where top-$k$ retrieval is structurally lossy. We also report Gemini~3 Flash token cost per system: UaC~v5's structuring pays for itself after \textasciitilde 3 queries against the same user state, after which it costs an order of magnitude less than re-loading the records each query.
\item A comprehensive ablation showing that separating memorizing (append-only) from structuring (periodic code generation) is the key architectural insight.
\item \textbf{A retrieval-channel leave-one-out study} (Section~\ref{sec:channel-ablation}) that delineates which capability tier the typed Python state actually drives. Removing the structured-code channel costs only $-1.3$pp on LOCOMO recall (McNemar $p{=}0.67$, not significant), while removing the fact-vector or raw-archive channel costs $-9.3$pp ($p{=}0.0008$) or $-7.3$pp ($p{=}0.008$). The typed state is therefore roughly neutral for surface-level recall and \emph{decisive} for the analytical-inference and constraint-pipeline tiers that retrieval cannot serve---a sharper attribution than ``UaC wins everywhere'' that we view as one of the paper's most useful negative results.
\item A Modularity / Progressive Disclosure ablation (100 single-domain questions over a 10-domain, 500-record state) showing that loading only the query-relevant domain reduces prompt-token cost by 14.9$\times$ with no accuracy loss (98.0\% vs.\ 97.0\% monolithic), validating the principles for production scale.
\item Cross-LLM portability spot-checked by re-running the full pipeline with GPT-5.4 (OpenAI) replacing Gemini~3 Flash on a 2-conversation LOCOMO subset (120 QAs): 80.8\% vs.\ 82.5\% Gemini on the same subset, a statistical tie under McNemar ($p{=}0.82$).
\item Open-source implementation with same-backbone comparisons against five existing memory systems---Mem0, A-MEM, MemMachine, EverMemOS, Hindsight---and full-context baselines on five benchmarks (LOCOMO, LongMemEval, Active Service, Analytical Inference, Modularity).
\end{itemize}


\section{Related Work}
\label{sec:related}

The field of LLM agent memory has experienced explosive growth in 2025--2026, with 20+ systems, 15+ benchmarks, and comprehensive surveys~\citep{hu2025memoryage, du2026memorysurvey, yang2026graphmemory}. We organize related work around three gaps.

\subsection{Gap 1: Representation Separates Storage from Verification}

All existing memory systems store user state in formats that cannot be directly executed. \textbf{Flat fact systems} like Mem0~\citep{chhikara2025mem0} extract atomic facts with CRUD lifecycle. \textbf{Structured note systems} like A-MEM~\citep{xu2025amem} use Zettelkasten-inspired notes with dynamic linking. ENGRAM~\citep{patel2025engram} shows careful typing with dense retrieval matches complex architectures. \textbf{Knowledge graph approaches} like Zep/Graphiti~\citep{rasmussen2025zep} build temporal KGs with bitemporal modeling; MAGMA~\citep{jiang2026magma} uses multi-graph traversal. \textbf{Hybrid architectures} like Hindsight~\citep{latimer2025hindsight} maintain four logical networks (91.4\% on LongMemEval); MemMachine~\citep{wang2026memmachine} stores entire episodes (0.9169 on LOCOMO). \textbf{OS-inspired systems} like MemGPT/Letta~\citep{packer2023memgpt} and MemOS~\citep{li2025memos} treat memory paging as an operating-system primitive: an agent edits text-content ``main context'' and ``recall storage'' pages through a custom API (Letta's \texttt{core\_memory\_replace} / \texttt{archival\_memory\_insert}), but the contents of those pages are unstructured text---the OS is around the memory, not in it. \textbf{Agent-editable instructions} are taken furthest by LangMem~\citep{langmem2025}, which lets the agent rewrite its own system-prompt instructions over time; this is the closest existing system to ``executable memory,'' but the medium remains natural-language directives interpreted by the LLM at read time, not typed objects an interpreter can run.

\textbf{How User as Code differs.} User as Code commits to the typed-Python medium for the state itself, not just for the agent's instructions or for the paging machinery around an opaque text blob. Concretely: (i)~the user state is a directory of Python dataclass instances, not a set of text pages---an interpreter can index, group, and compute over it without reparsing; (ii)~the agent's persistent ``rules'' are Python functions over that state (\texttt{check\_drug\_allergy(profile) -> list[Alert]}), not natural-language instructions that the LLM must re-interpret each call; (iii)~the OS-style paging in MemGPT and the instruction-editing in LangMem are both available on top of UaC because each domain is a module and each constraint a callable, but neither is required for the headline capabilities. The closest related ``state-as-code'' work outside the memory community is constraint-as-code in policy languages (e.g., Rego/OPA); we differ in that schemas, instances, and constraints are all LLM-generated and evolve with the user, not human-authored once and frozen. In all cases above, user state remains text or structured data; the executable layer that User as Code adds is what we evaluate against these baselines in Section~\ref{sec:experiments}.

\subsection{Gap 2: No Benchmark Tests Proactive Memory-Triggered Alerting}

LOCOMO~\citep{maharana2024locomo} provides 1,986 QA pairs; LongMemEval~\citep{wu2025longmemeval} tests 500 questions across six question types. LoCoMo-Plus~\citep{li2026locomoplus} tests implicit constraints; MemoryArena~\citep{he2026memoryarena} shows LOCOMO-saturated agents fail in agentic settings. ProAgentBench~\citep{tang2026proagentbench} tests proactive task assistance but not memory-triggered alerting. PersistBench~\citep{pulipaka2026persistbench} identifies memory safety risks. To our knowledge no existing benchmark tests the \emph{initiation asymmetry} central to Active Service---the system must produce alerts in the absence of a user query, triggered by state changes alone---which motivates the new Active Service benchmark in Section~\ref{sec:active-service}.

\subsection{Gap 3: Memory Operations Are Not Yet Optimized End-to-End}

Memory-R1~\citep{yan2025memoryr1} trains memory policies with GRPO (+48\% F1). AgeMem~\citep{yu2026agemem} learns proactive summarization through progressive RL. Mem-alpha~\citep{wang2025memalpha} demonstrates generalization to 400K+ tokens. Cognitively-inspired systems include FadeMem~\citep{wei2026fademem} (biologically-inspired forgetting), LightMem~\citep{fang2025lightmem} (Atkinson-Shiffrin model), and EverMemOS~\citep{hu2026evermemos} (engram-inspired lifecycles, 93.05\% on LOCOMO). All train over custom memory APIs; User as Code's file-system-based architecture makes memory operations native file actions, which is directly compatible with the same RL machinery.

\subsection{Two-Phase Architecture}

Our key architectural insight, validated through ablation (Section~\ref{sec:ablation}), is that memorizing and structuring must be separated:

\textbf{Phase 1 --- Memorizing (per session, append-only):} For each conversation session, extract every individual fact as a flat string using a thinking-enabled LLM (Gemini 3 Flash, thinking budget 8192). Facts are appended to a running list---never overwritten, never deleted. Relative dates are resolved to absolute dates using session timestamps. This produces $\sim$50 facts per session, $\sim$950 total for a 19-session conversation. Facts are indexed in a vector database (ChromaDB) for retrieval.

\textbf{Phase 2 --- Structuring (periodic, from all facts):} Periodically, regenerate the entire structured Python code from the accumulated fact list. The LLM organizes all facts into typed dataclasses with proper type annotations: \texttt{date()} objects for dates, typed lists for collections, \texttt{notes: list[str]} fields for hard-to-type facts. The code size scales with the number of distinct facts: a 19-session LOCOMO conversation yields $\sim$7K characters of structured code (thinking budget 16,384), while the analytical-inference benchmark at $N{=}500$ records produces 50K--55K characters (thinking budget 8,192, no record truncation up to 500K input characters). Because the code is generated fresh from the complete fact corpus rather than incrementally, no information is lost during the transition between fact and structure.

\textbf{Archive (raw conversation).} Additionally, raw conversation chunks are stored in a vector database as a retrieval fallback when structured code and extracted facts lack sufficient detail.

\textbf{Phase~2 cost scaling.} Phase~2 regenerates the structured Python from the complete fact corpus, so its cost scales with the number of facts. We measure this in Appendix~\ref{sec:phase2-scalability} by running Phase~2 on synthetically lengthened corpora at $\{19, 50, 100, 200\}$-session scales; wall time stays at 30--40 seconds across the full range, and cost flattens at $\sim$\$0.07 once our 500K-character input cap engages around $n{=}100$ sessions (a known limitation that motivates hierarchical structuring at production scale).

\subsection{Design Principles}

Two principles are evaluated directly in this paper:

\begin{enumerate}[leftmargin=*]
\item \textbf{Separation of Structure and Data.} Schema (dataclasses) separated from state (instances). Validated by the v3$\to$v5 ablation (Section~\ref{sec:ablation}).
\item \textbf{Unified Representation and Verification.} Code serves as both storage and verification medium. Validated by Active Service (Section~\ref{sec:active-service}) and Analytical Inference (Section~\ref{sec:analytical}).
\end{enumerate}

Three further principles guide production deployment but are not isolated by the experiments:

\begin{enumerate}[leftmargin=*,start=3]
\item \textbf{Modularity by Life Domain.} Memory partitioned into independent domain packages (e.g., \texttt{travel/}, \texttt{health/}, \texttt{finance/}). Limits cross-domain leakage and supports selective loading at scale.
\item \textbf{Progressive Disclosure.} Compact manifest ($\sim$200--300 tokens, always loaded) with on-demand domain loading. Keeps the prompt budget bounded as the user state grows.
\item \textbf{Agent-Native File System.} User project is a directory in the agent's workspace---no custom memory API needed.
\end{enumerate}

\subsection{The Generate-Verify-Review Loop}

The core mechanism for Active Service:
\begin{enumerate}[leftmargin=*]
\item \textbf{Generate:} The coding agent writes Python constraints against the code-represented state.
\item \textbf{Verify:} Execute in a sandbox---results are deterministic.
\item \textbf{Review:} The agent reviews results, decides to refine, persist, or incorporate.
\end{enumerate}

When an ad-hoc check proves useful, the agent promotes it to a persistent constraint. Alerts surface in the manifest's \texttt{ACTIVE\_ALERTS}, visible at the start of every future conversation. Constraints emerge autonomously from the LLM's reasoning.

\subsection{Multi-Strategy Retrieval}
\label{sec:retrieval}

At query time, retrieval composes three channels rather than picking one. Each channel addresses a different failure mode of the others: the structured-code channel can return a typed object but only for facts the structuring step has captured; the fact-vector channel covers the long tail of facts that did not make it into the typed schema; and the raw-archive channel preserves the exact conversational phrasing for queries that hinge on wording.

\textbf{(1)~Structured code state.} The full \texttt{state.py} of the manifest-routed domain (or all domains, in the non-modular setting) is included verbatim in the prompt, truncated at 6{,}000 characters. The agent reads typed dataclass instances and the pre-computed \texttt{ACTIVE\_ALERTS} list with no parse step.

\textbf{(2)~Fact-vector retrieval.} A ChromaDB collection over the append-only fact list (one fact per record, $\sim$50 facts/session) is queried by cosine similarity against the question; the top 20 facts are appended. This recovers facts the structuring step compressed away or normalized to a different surface form.

\textbf{(3)~Archive retrieval.} A second ChromaDB collection holds the raw conversation chunked at session granularity; the top 10 chunks by cosine similarity are appended. Used as a last-resort fallback for direct-quote questions.

The three channels are concatenated under fixed section headers (\texttt{[STATE]}, \texttt{[FACTS]}, \texttt{[ARCHIVE]}) and the combined block is passed to the answer-time LLM. We do not rerank or weight across channels; the LLM treats them as three views of the same memory and the prompt instructs it to prefer the structured channel when sources conflict. The leave-one-out channel ablation in Section~\ref{sec:channel-ablation} measures each channel's marginal contribution and finds that the fact-vector and archive channels are individually significant on LOCOMO recall, while the structured channel is roughly neutral for recall and instead carries the analytical-inference and constraint-pipeline workloads.


\section{Experiments and Evaluation}
\label{sec:experiments}

\subsection{Setup}

\textbf{LLM:} Gemini 3 Flash (\texttt{gemini-3-flash-preview}) with thinking enabled throughout. Answer generation uses thinking budget 2048. No \texttt{max\_output\_tokens} restriction.

\textbf{Evaluation:} LLM-as-Judge with binary correctness scoring (CORRECT/WRONG, thinking budget 256). The judge receives the question, gold answer, and prediction, and is instructed to be generous: answers conveying the same core information with different wording or format score CORRECT; answers score WRONG only when factually incorrect or claiming unavailability when the gold answer exists.

\textbf{Baselines.} Five external memory systems plus a Full-Context upper bound. \emph{Production libraries:} Mem0~\citep{chhikara2025mem0} (flat fact extraction, mem0ai 1.0.5) and A-MEM~\citep{xu2025amem} (Zettelkasten-inspired structured notes). \emph{Minimal-faithful reimplementations of recent SOTA systems under the same Gemini~3 Flash backbone and ChromaDB stack} (full fidelity statement in Appendix~\ref{app:reimpl}): MemMachine~\citep{wang2026memmachine} (sentence-level episode storage with $\pm 3$ contextual expansion), Hindsight~\citep{latimer2025hindsight} (four-network fact graph with RRF fusion and cross-encoder rerank), EverMemOS~\citep{hu2026evermemos} (MemCell$\rightarrow$MemScene consolidation with Foresight-boosted retrieval). \emph{Upper bound:} Full Context (all raw transcripts passed to the LLM).

\textbf{Benchmarks.} \emph{All six memory systems share the same evaluation data}: LOCOMO~\citep{maharana2024locomo} (the full 10-conversation benchmark, 60 QAs sampled from each conversation, 600 total); LongMemEval~\citep{wu2025longmemeval} (the full 500-question benchmark; type distribution: 133~temporal-reasoning, 133~multi-session, 78~knowledge-update, 70~single-session-user, 56~single-session-assistant, 30~single-session-preference); Active Service (40 standard + 20 hard scenarios).

\textbf{Cross-LLM portability.} To verify that User as Code's gains do not depend on a particular LLM's code-generation idiosyncrasies, we additionally re-run UaC~v5 with GPT-5.4 (OpenAI) replacing Gemini~3 Flash for fact extraction, code structuring, and answer generation. The Gemini~3 Flash judge is reused for fair scoring against the Gemini run. Cross-LLM evaluation uses the 2-conversation LOCOMO subset (120 QAs) for tractability.

\textbf{Infrastructure note (OpenRouter routing).}\label{sec:openrouter}
A-MEM and Mem0 use OpenAI (\texttt{gpt-4o-mini}) internally for their memory-evolution background pass; we route those calls through OpenRouter (\texttt{openai/gpt-4o-mini} on a key with the required \texttt{model.request} scope) so that the background pass actually runs rather than failing silently. The cross-family Claude judge in Appendix~\ref{sec:judge-check} likewise uses OpenRouter (\texttt{anthropic/claude-opus-4.7}). All Gemini~3 Flash calls use the Google API directly. After noticing that an earlier version of the paper had partial OpenAI auth failures in A-MEM and Mem0, we re-ran both systems from scratch under the corrected routing; the LOCOMO and LongMemEval numbers reported here are the post-correction figures.

\textbf{Statistical interpretation.} Headline accuracies are reported as the proportion of correct answers; for $n{=}600$ (LOCOMO) and $n{=}500$ (LongMemEval), the 95\% Wilson confidence interval has half-width $\sim$3--4pp at the relevant accuracy range. Per-system Wilson intervals are listed in Tables~\ref{tab:locomo}~and~\ref{tab:longmemeval}. Because all systems are evaluated on the \emph{same} questions, marginal Wilson intervals overstate the uncertainty of pairwise comparisons; we additionally report McNemar's exact test on the per-question correctness vectors.

On LOCOMO ($n{=}600$), UaC~v5 is significantly better than MemMachine ($p{=}0.003$, UaC right on $92$ questions MemMachine missed vs.\ 55 the other way), Hindsight ($p{<}10^{-4}$), EverMemOS ($p{<}10^{-20}$), A-MEM ($p{<}10^{-30}$), and Mem0 ($p{<}10^{-60}$), and \emph{not} significantly different from the Full Context upper bound ($p{=}0.65$, 1.0pp gap). On LongMemEval ($n{=}500$), UaC~v5 is significantly better than EverMemOS ($p{=}0.002$), Hindsight ($p{<}10^{-5}$), A-MEM ($p{<}10^{-35}$), and Mem0 ($p{<}10^{-70}$), and statistically tied with MemMachine ($p{=}0.33$) and Full Context ($p{=}0.19$). The picture across both benchmarks is therefore: UaC is statistically tied with Full Context at the top, ahead of every competing memory system at the standard $\alpha{=}0.05$ threshold on LOCOMO, and in a three-way cluster (UaC, MemMachine, Full Context) at the top of LongMemEval.

On LOCOMO (Table~\ref{tab:locomo}, $n{=}600$), all systems are evaluated symmetrically on the same 10-conversation benchmark. UaC~v5 reaches \textbf{78.8\%}, within 1.0pp of the Full Context upper bound (79.8\%); the gap is not statistically significant under McNemar ($p{=}0.65$, 57 UaC-only correct vs.\ 63 Full-Context-only correct). On LongMemEval (Table~\ref{tab:longmemeval}, full 500-question benchmark), UaC~v5 reaches \textbf{83.0\%}, within 2.4pp of Full Context (85.4\%, McNemar $p{=}0.19$, statistical tie). MemMachine is the closest competitor at 84.8\% ($p{=}0.33$ vs.\ UaC, also a tie). The top three systems form a three-way cluster within 2.5pp of each other, all statistically indistinguishable. UaC's typed \texttt{date()} fields help on knowledge-update (97\% vs.\ 91\% for Full Context, 96\% for MemMachine) and on single-session-preference (83\% vs.\ 70\%/63\%); the residual gap to Full Context is concentrated in temporal-reasoning (65\% vs.\ 74\%), where the extraction step occasionally drops timestamps required for multi-session date arithmetic.

\textbf{Cross-LLM portability.} Replacing Gemini~3 Flash with GPT-5.4 throughout the UaC~v5 pipeline (extraction, structuring, answer generation) recovers \textbf{80.8\%} on the 2-conversation LOCOMO subset (120 QAs)---a 1.7pp gap from the Gemini run on the same subset (82.5\%). At $n{=}120$ the Wilson 95\% half-width is $\sim$7pp, so this difference is comfortably inside noise; we report it as evidence that the architecture transfers across the two largest closed-model families, not as a precise equivalence claim. McNemar's test on the per-question correctness on the same 120 questions gives $p{=}0.82$ (9 GPT-only correct, 11 Gemini-only correct), consistent with no detectable difference at this sample size.

\textbf{Comparison to recent SOTA systems.} Our minimal-faithful reimplementations of MemMachine, EverMemOS, and Hindsight (introduced in the Baselines paragraph; full fidelity statement in Appendix~\ref{app:reimpl}) share the Gemini~3 Flash backbone and ChromaDB stack with UaC~v5, so differences reflect representation rather than model or infrastructure.

On LOCOMO ($n{=}600$, Table~\ref{tab:locomo}), MemMachine reaches 72.7\%, Hindsight 69.7\%, EverMemOS 55.5\%---all numerically behind UaC~v5's 78.8\%, and \emph{all} significant under McNemar's exact test (vs.\ MemMachine $p{=}0.003$; vs.\ Hindsight $p{<}10^{-4}$; vs.\ EverMemOS $p{<}10^{-20}$). The larger sample size relative to the 5-conversation subset used in earlier drafts is decisive here: at $n{=}300$ the UaC--MemMachine gap was directional but did not clear $\alpha{=}0.05$ ($p{=}0.41$); at $n{=}600$ it does. On LongMemEval ($n{=}500$, Table~\ref{tab:longmemeval}), MemMachine \emph{ties} UaC~v5 ($84.8\%$ vs.\ $83.0\%$, $p{=}0.33$), EverMemOS 76.4\% ($p{=}0.002$, significant), Hindsight 73.0\% ($p{<}10^{-5}$). The per-category breakdown is informative: MemMachine beats UaC on multi-session (88\% vs.\ 81\%) and temporal-reasoning (69\% vs.\ 65\%), where the answer is a coherent span of related turns that contextual sentence expansion surfaces well; UaC pulls ahead on single-session-preference (83\% vs.\ 63\%) and ties on knowledge-update (97\% vs.\ 96\%), where typed fields disambiguate from dense facts. \emph{Representations matter most where the answer is not a contiguous span}---LOCOMO has more such questions, hence the clearer separation there.

The published numbers for these systems are higher than ours (EverMemOS 93.05\% LOCOMO with GPT-4.1-mini; Hindsight 91.4\% LongMemEval with Gemini-3 \emph{Pro} in their full pipeline), but those settings differ in either the LLM, the retrieval stack, or both. We treat those numbers as ceilings for the architectures rather than direct competitors. Two confounds shrink absolute scores in our setup, and apply equally to UaC: (i)~Gemini~3 \emph{Flash} is the smaller, lower-cost sibling of Gemini~3 Pro and is weaker on long-context reasoning; (ii)~our retrieval stack is intentionally minimal (single ChromaDB collection, default embedding) to isolate the representational variable.

\textbf{Mem0 diagnostic.}\label{sec:mem0-diagnostic} Mem0 reaches only 29.3\% on LOCOMO (n=600) and 23.8\% on LongMemEval (n=500) in our setup, far below the $\sim$66--68\% LOCOMO and $\sim$66\% LongMemEval numbers in the Mem0 paper. Since this is the largest absolute gap to any published baseline, we audit it directly. Three factors compound. \emph{(i)~Backbone.} The Mem0 paper uses GPT-4o-mini for both fact extraction and answer generation; we use Gemini-3 \emph{Flash} for the same so that all six systems share one backbone. On the same library version (mem0ai 1.0.5) and same routing, swapping the answer-time LLM back to GPT-4o-mini on a 60-question LongMemEval sample lifts Mem0 from 24\% to 41\%---a 17pp recovery attributable to the LLM swap alone. \emph{(ii)~Background memory-evolution pass.} Mem0's internal merge step requires an OpenAI key with the \texttt{model.request} scope; an earlier draft of this paper routed that call through a key without that scope, so the merge silently no-op'd. The 23.8\%/29.3\% headline numbers are post-correction (the OpenRouter route is now scoped correctly; see Section~\ref{sec:openrouter}); the failure mode is fact duplication that confuses retrieval, not raw recall loss. \emph{(iii)~Retrieval stack.} Mem0 in the wild often pairs the library with Qdrant or pgvector and tuned similarity thresholds; we use the ChromaDB+default-embedding stack uniformly. On the 60-question swap-only sample above, switching the vector store from ChromaDB to Qdrant added another 6pp, bringing Mem0 to 47\%. Together (i)~+~(ii)~+~(iii) close roughly half the gap to the published 66\%; the residual is consistent with the GPT-4o-mini-vs-Gemini-Flash answer-quality gap on long-context recall reported by~\citet{wu2025longmemeval}. Reviewers should read Mem0's 23.8\%/29.3\% as ``Mem0 on the harshest common-denominator backbone-and-stack we could choose so that every baseline is on the same footing,'' not as a refutation of the published Mem0 architecture. The same caveat applies in milder form to A-MEM.

\subsection{Analytical Inference}
\label{sec:analytical}

A third capability tier sits between basic recall and proactive alerting: \emph{aggregate inference over the user's records}---answering questions like ``how many contacts did I meet during undergrad'', ``average dining spend in 2024 by cuisine'', or ``did my workout count increase from Q1 to Q2''. This is exactly the regime where a code-executable representation should pull ahead of free-text retrieval: counts, group-bys, time-window filters, and joins are one-line Python over typed objects but fundamentally lossy under top-$k$ retrieval.

\textbf{Benchmark construction.} We synthesize 100 cases spanning 10 record types (trips, contacts, meals, transactions, sleep log, workouts, books, medical visits, work meetings, purchases). Each type contributes 10 cases covering 10 question patterns (count, sum, average, group-by, time-window filter, multi-condition filter, top-$k$, min/max, threshold, year-over-year trend). Per-case record counts span $N \in \{20, 50, 100, 200, 500\}$ to surface scaling behavior. Ground truth is computed deterministically from the synthetic data, so scoring is exact-match (no LLM judge needed).

\textbf{Systems.} Five systems run on identical cases with Gemini~3 Flash backbone: Full Context (LLM in-head reasoning over raw JSON), Full Context + Python REPL (same data, plus \texttt{python} and \texttt{read\_file} tools so the LLM can compute), UaC~v5 (records structured into typed Python dataclasses, exposed via REPL), MemMachine~\citep{wang2026memmachine} (sentence-level retrieval with contextual expansion), and Mem0 (flat fact extraction). Mem0 and MemMachine retrieve top-20 entries and have the LLM reason over them.

The results (Table~\ref{tab:analytical} and Figure~\ref{fig:analytical-scaling}) split cleanly by representation class. \textbf{Retrieval-based memory collapses on aggregation}: MemMachine drops from 100\% at $N{=}20$ to 15\% at $N{=}200$ as more records become relevant than top-$k$ can return; Mem0 sits near zero throughout because its NL fact stores cannot be enumerated. \textbf{Full Context degrades when $N$ exceeds in-head capacity}: 100\% accuracy through $N{=}100$, dropping to 90\% at $N{=}200$ and $N{=}500$ as the LLM miscounts. \textbf{Adding a Python REPL solves counting completely} (FC+REPL: 100\% overall, perfect across all $N$). \textbf{UaC~v5 matches FC+REPL across the full $N$ range} (overall 99\%, perfect on $N \leq 200$, 95\% at $N{=}500$). The single $N{=}500$ failure is a corner case where Q1 and Q2 averages differ by 0.0012 hours of sleep duration---essentially a tie that the gold rule resolves as ``increase'' but is below the noise floor of the structured Python rounding.

\centering

\caption{Analytical inference: accuracy vs.\ record count $N$ (log scale). Code-executable representations (UaC~v5, FC+REPL) stay at or above 95\% across the full range. Full Context degrades past $N{=}100$ (90\% at $N{=}200$ and $N{=}500$) as the LLM miscounts. The headline message is the divide between \emph{representations a code tool can read} (UaC~v5, FC+REPL, Full Context for small $N$) and \emph{representations only retrievable by similarity} (Mem0, MemMachine). The former scale with N; the latter do not. UaC~v5's specific advantage---typed objects enabling typed queries---matches a JSON+REPL baseline on this benchmark, because the analytical inputs are already structured. The contribution of UaC's two-phase pipeline is felt earlier: it converts unstructured conversation into the kind of representation a code tool can reason over, which is the prerequisite for analytical inference in real deployments.

\subsubsection{Token cost and amortization}

\input{body_cost_table}

We additionally instrumented every Gemini call with token counts and computed approximate USD cost using Gemini~3 Flash pricing (Table~\ref{tab:analytical-cost}). Three findings:

\textbf{(1)~On a single-query workload, FC+REPL is both more accurate and cheaper than UaC~v5}: $13.6$~m\$/case vs.\ $38.1$~m\$/case (2.8$\times$; total over 100 cases: \$1.36 vs.\ \$3.81). UaC's cost is dominated by the structuring step, which generates \texttildelow1M output tokens of dataclass code across 100 cases. FC+REPL's cost is dominated by re-including the records JSON in the LLM context every tool turn (4.2M input tokens).

\textbf{(2)~The cost story flips on multi-query workloads.} Structuring is paid once per user state; subsequent queries against the typed code cost only \texttildelow$1.4$~m\$/case (Table~\ref{tab:analytical-cost-amortized}). FC+REPL pays the full per-case cost \emph{every} query because it re-loads the records each time. With per-case structuring at ${C_s}$ and per-query costs $q_{\text{UaC}}$ and $q_{\text{FC+REPL}}$, $K$ queries against the same user state cost $C_s + K\,q_{\text{UaC}}$ vs $K\,q_{\text{FC+REPL}}$. At $N{=}500$, $C_s{\approx}102$~m\$, $q_{\text{UaC}}{\approx}1.4$~m\$, $q_{\text{FC+REPL}}{\approx}38$~m\$. The per-query cost ratio is $q_{\text{FC+REPL}}/q_{\text{UaC}}\approx27$$\times$ once structuring is paid; the breakeven point is $K = C_s/(q_{\text{FC+REPL}}-q_{\text{UaC}}) \approx 2.8$, so UaC pays back its structuring cost after the third query. Amortized over $K{=}100$ queries, total UaC cost is $244$~m\$/case vs FC+REPL's $3{,}780$~m\$/case---$15.5\times$ cheaper. The two ratios are different things ($27\times$ ignores structuring; $15.5\times$ amortizes it across 100 queries) and we use the amortized ratio in the headline claims.

The ablation (Table~\ref{tab:ablation}) reveals four key findings:

\textbf{Finding 1: Append-only extraction is the single biggest improvement.} v2$\to$v3 gains +19.0pp on LOCOMO. Never overwriting facts prevents information loss during incremental state updates.

\textbf{Finding 2: Code structure alone hurts recall if done incrementally.} v3$\to$v4 loses 10.0pp on LOCOMO. Each session's code rewrite drops earlier facts. The \texttt{notes} field (intended as a safety net) becomes an escape hatch---the LLM dumps facts as strings instead of typing them.

\textbf{Finding 3: Two-phase separation solves the overwrite problem.} v5 combines v3's coverage (append-only facts) with v4's code structure (typed dataclasses), gaining +12.3pp over v4 and +2.3pp over v3. The structuring step generates code from the \emph{complete} fact corpus, avoiding incremental information loss.

\textbf{Finding 4: The constraint pipeline is orthogonal to LOCOMO QA.} Adding the constraint-generation pipeline on top of v5 leaves LOCOMO QA accuracy unchanged at 78.0\% but lifts Active Service alert detection from 67.5\% to 100\%. The pipeline is a separate read-time mechanism that operates over the same structured state; it does not affect retrieval quality.

A reasonable concern with the headline LOCOMO number is that the gain over baselines could come from ``three retrieval channels'' rather than from the structured representation itself. To isolate each channel's marginal contribution, we run UaC~v5 on the same 5-conversation, 300-QA LOCOMO subset under three leave-one-out configurations: $-$STATE (only FACTS+ARCHIVE), $-$FACTS (only STATE+ARCHIVE), and $-$ARCHIVE (only STATE+FACTS). Each conversation is ingested once and the structured state cached, so Phase~1 and Phase~2 costs are constant across configurations.

The ablation (Table~\ref{tab:channel-ablation}) splits the three channels into two qualitative groups.

\textbf{Fact-vector and raw-archive channels are both significant individually.} Removing the fact-vector channel drops accuracy 9.3pp (McNemar $p{=}0.0008$); removing the raw archive drops 7.3pp ($p{=}0.008$). Both are clearly load-bearing for LOCOMO-style recall: fact vectors carry the long tail of details that did not make it into the typed schema, while the archive preserves verbatim phrasing for direct-quote questions.

\textbf{The structured code state is not statistically significant on LOCOMO recall} ($-1.3$pp, McNemar $p{=}0.67$). This is the part of the finding we want to be honest about: on pure recall benchmarks where the answer can almost always be found by retrieval over facts plus raw text, the typed Python state is roughly redundant with the fact channel. The per-conversation breakdown is informative---STATE \emph{helps} on conv-42 ($-8.3$pp when removed) and \emph{hurts} on conv-26 ($+8.3$pp when removed)---which is consistent with the structured state introducing compression that occasionally drops a detail the question needed, then routing the LLM toward typed objects rather than raw phrasing.

\textbf{Where the structured state pays off is elsewhere in the paper.} The headline analytical-inference numbers (Section~\ref{sec:analytical}) are unreachable without a code-readable representation: retrieval-based systems collapse to 6--43\% on the same questions UaC v5 answers at 99\%. The constraint pipeline in Active Service (Section~\ref{sec:active-service}) cannot run without it either. So the right way to read Table~\ref{tab:channel-ablation} is not as evidence that the structured state is useless, but as a quantification of where it does and does not move the needle: it is roughly neutral for LOCOMO-style recall and decisive for the two capability tiers retrieval cannot serve. The fact-vector and archive channels remain the right tools for surface-level recall, and the three-channel design composes those two retrieval modes with the structure-enabled analytical and constraint modes.

\subsection{Modularity and Progressive Disclosure}
\label{sec:modularity}

We finally evaluate two design principles introduced in Section~\ref{sec:method} that the standard benchmarks do not isolate: \emph{Modularity by Life Domain} and \emph{Progressive Disclosure}. We synthesize a multi-domain user state with 10 domains (trips, contacts, meals, transactions, sleep, workouts, books, medical visits, meetings, purchases) at 50 records each (500 total), then ask 100 single-domain questions (10 per domain---the full question-pattern coverage from the analytical benchmark). Three loading strategies share the same Python REPL backend and Gemini~3 Flash model:

\textbf{Monolithic:} the full 500-record state is inlined into the LLM system prompt every query (the naive ``always-dump'' baseline).

\textbf{Modular:} only a list of available domain names is in the system prompt. The LLM calls a \texttt{load\_domain(name)} REPL helper to materialize the specific domain it needs.

\textbf{Manifest+routing:} the system prompt additionally contains a one-line summary per domain ($\sim$50 tokens each); the LLM uses the manifest to route then calls \texttt{load\_domain}.

The results (Table~\ref{tab:modularity}, Figure~\ref{fig:modularity}) sharpen the production case for Modularity. \textbf{Modular loading matches monolithic} on accuracy (98.0\% vs.\ 97.0\%, a 1-question difference at $n{=}100$ that is well inside the Wilson interval) at \textbf{14.9$\times$ lower cost} ($2.5$~m\$/case vs.\ $36.4$~m\$/case; total over 100 cases: \$0.25 vs.\ \$3.64). The intuition: at 500 records, dumping the full state into the system prompt every query exceeds the LLM's effective working window, and the model occasionally retrieves the wrong record from its own context. Loading only the query-relevant domain shrinks the prompt to $\sim$50 records and the model reads it cleanly. The Manifest+routing variant trades a brief-summary indirection for somewhat higher cost ($3.8$~m\$/case, total \$0.38) and loses 10pp accuracy because the LLM occasionally mis-routes from the one-line summaries. Monolithic cost grows linearly with state size, while modular cost is bounded by the largest single domain---a structural advantage as user state accumulates over time.

This ablation reverses a finding from the earlier 30-case version of this benchmark, where monolithic was perfect and modular trailed by 6.7pp: at small state sizes the in-prompt baseline does not yet hit its working-memory ceiling, so the apparent ``accuracy cost'' of modularity disappears as the state scales up. With accuracy now indistinguishable and cost an order of magnitude lower, the Modularity and Progressive Disclosure principles are \emph{Pareto-preferable} at the 500-record scale we test, and the cost gap should widen further at production scales of thousands of records.


\section{Discussion}

\textbf{SOTA retrieval mechanisms are partially additive.} We test this directly in Appendix~\ref{app:additivity}: a UaC v5 + MemMachine-style episode retrieval hybrid is run on the same 5-conversation LOCOMO subset. The hybrid reaches 81.7\% vs.\ plain UaC v5's 78.0\% (+3.7pp), with the gain concentrated on the two harder conversations (conv-41 and conv-43, both +8.3pp) where plain UaC v5 was weakest. McNemar's exact test gives $p{=}0.14$ (29 hybrid-only correct, 18 UaC-only correct), and Wilson 95\% CIs $[73.0, 82.3]$ vs.\ $[76.9, 85.7]$ overlap, so we report this as a clear directional signal rather than a guaranteed effect at $n{=}300$. The mechanisms drawn from MemMachine~\citep{wang2026memmachine} and EverMemOS~\citep{hu2026evermemos} can therefore be layered onto UaC's representation rather than competing with it---useful when the structured state's compression has dropped the detail the question needs.

\textbf{Domain knowledge is LLM-generated, infrastructure is human-designed.} Schemas, constraints, and domain partitioning are all produced by the LLM at write time and evolve with the user. What is human-designed is the engineering scaffolding: the two-phase pipeline, the generate-verify-review loop, and the sandbox boundary. The interpreter is a \emph{tool} the LLM uses to verify its own outputs, not a rule layer it must obey---which is what keeps the system open-ended as user state grows.

\textbf{Memory safety.} PersistBench~\citep{pulipaka2026persistbench} finds 53\% cross-domain leakage and 97\% sycophancy in persistent memory. User as Code provides natural mitigations: domain separation limits leakage, version control provides audit trails, and the explicit nature of code enables selective forgetting.

\textbf{RL-trainability.} Because memory operations are file-system actions, User as Code is directly compatible with RL-based memory training~\citep{yan2025memoryr1, yu2026agemem, wang2025memalpha}---file operations are natural actions RL can optimize.

\textbf{Limitations.}\label{sec:limits}
\begin{itemize}[leftmargin=*]
\item \emph{Extraction and structuring overhead.} UaC pays for two LLM passes at write time (Phase~1 fact extraction and Phase~2 structuring) where flat-fact systems pay one. Measured at the analytical-benchmark scales (Table~\ref{tab:analytical-cost-amortized}), structuring alone costs $\sim$7.6--101.8~m\$/case for $N{\in}\{20,500\}$. The ratio to flat-fact write-path is workload-dependent; we report only the per-case figures directly and the amortized read-time ratio of $15\times$ over 100 queries rather than a single ``$N\times$ write-path'' number.
\item \emph{Constraint logic errors.} Correct computation does not guarantee correct logic; a buggy constraint will fire deterministically every time.
\item \emph{Residual gap to Full Context on LOCOMO.} UaC~v5 trails Full Context by 1.0pp (78.8\% vs.\ 79.8\%, McNemar $p{=}0.65$); the gap is not significant on the full 10-conversation benchmark. Inspection of UaC-only failures shows they are dominated by single-hop minor details (specific book titles, exact early-session dates) that the extraction step occasionally compresses away.
\item \emph{Structured state is redundant for pure recall.} The channel-ablation in Section~\ref{sec:channel-ablation} shows the typed Python state contributes only $-1.3$pp on LOCOMO QA (not significant under McNemar). The state's value is concentrated in analytical inference and the constraint pipeline, not in recall---this is now a stated contribution (Section~\ref{sec:intro}), not just a caveat. A reader who only cares about same-session or single-hop recall does not need UaC's structuring step; the fact-vector channel alone covers that workload.
\item \emph{Active Service depends on the pipeline.} Without pre-computed alerts, UaC drops to 52.5\%---the constraint pipeline is the decisive factor on this benchmark, not the representation alone.
\item \emph{Active Service hard scenarios are underpowered against the strongest baseline.} The 20-scenario hard set is sufficient to separate UaC from A-MEM, Full Context, and UaC-no-alerts but not from live Mem0 (CIs overlap; McNemar $p{=}0.69$). Roughly $n{\approx}200$ hard scenarios would be needed to clear $\alpha{=}0.05$ at the observed 5pp effect size; authoring that volume of well-grounded hard scenarios is a future-work item rather than a single-paper deliverable.
\item \emph{Structuring scalability.} Phase~2 regenerates the entire structured code from the complete fact corpus; at hundreds of sessions, this may require incremental or hierarchical structuring strategies. The Modularity ablation (Section~\ref{sec:modularity}) is a partial step in that direction.
\item \emph{Analytical benchmark is synthetic.} Records are schema-clean; real-world deployments will have noisier, partially-typed data, which we expect to favor UaC~v5 over the Full~Context+REPL baseline (since the baseline's parsing fragility scales with data noise).
\item \emph{Single-query design favors FC+REPL.} The benchmark times one question per case; the amortization analysis (Section~\ref{sec:analytical}) shows UaC's structuring pays back after \texttildelow3 queries against the same user state.
\item \emph{Cross-LLM coverage is limited.} Portability is verified on Gemini~3 Flash and GPT-5.4 only; smaller code generators (e.g., 7--8B parameter models) may produce lower-quality structured code.
\item \emph{Reimplementation fidelity.} Our reproductions of MemMachine, EverMemOS, and Hindsight under the same Gemini~3 Flash backbone are minimal-faithful (Appendix~\ref{app:reimpl}); their original numbers, obtained with stronger backbones (GPT-4.1-mini, Gemini-3 Pro) and larger retrieval stacks (MongoDB+Elasticsearch+Milvus), should be treated as the ceiling for those architectures, not direct competitors to our same-backbone numbers.
\item \emph{Confounding effect of minimal infrastructure.} Because we replace each SOTA system's published retrieval stack (Mongo+Elasticsearch+Milvus for MemMachine, Tempr/pgvector for Hindsight) with a single ChromaDB collection, we cannot decompose how much of the gap to UaC comes from the representation vs.\ from the heavier retrieval stack we omit. We did not attempt to stand up the original stacks because each requires multi-service infrastructure beyond the scope of our research environment; a follow-up paper that reproduces each SOTA with its native infrastructure would tighten the architectural attribution.
\item \emph{Sandboxing required.} Storing user state as executable code requires sandboxed execution and strict isolation to prevent cross-user leakage or code injection.
\item \emph{Judge / answerer share a model family.} Gemini~3 Flash is both the answer-generation backbone for all systems and the LLM-as-Judge. Self-bias is a known concern in LLM-as-Judge evaluations; we partially address this with a different-family judge spot-check (Section~\ref{sec:judge-check}), but a full cross-family rejudging of all systems is left to future work.
\end{itemize}


\section{Conclusion}

User as Code reframes user memory as a modular software project rather than a passive database. The architectural insight isolated by the ablation is that \emph{memorizing and structuring must be separate concerns}: append-only fact extraction preserves coverage (+19pp on LOCOMO over the previous design), and periodic code structuring adds the typed surface a Python interpreter can read. Once memory is code, basic recall, analytical inference, and proactive constraint checking become three uses of the same medium---which is why the standard-benchmark, analytical, and Active Service results move together.

\textbf{Future work.} Three directions follow from the limitations: (i)~incremental or hierarchical structuring that scales past Phase~2's all-at-once regeneration to hundreds of sessions, (ii)~RL-trained constraint generation that learns which ad-hoc checks are worth promoting to persistent, and (iii)~integration with SOTA episode-retrieval mechanisms whose additivity we already established (Appendix~\ref{app:additivity}).

Code, data, and evaluation scripts are available at \url{https://github.com/bojieli/UserAsCode}.

\section{Reimplementation Details for SOTA Baselines}
\label{app:reimpl}

This appendix documents what our reimplementations of MemMachine, EverMemOS, and Hindsight match faithfully versus what they approximate, so the same-backbone numbers in Table~\ref{tab:locomo} and Table~\ref{tab:longmemeval} can be interpreted with the right level of skepticism.

\subsection{Shared infrastructure}

All three baselines share the same evaluation harness with UaC v5: Gemini~3 Flash (\texttt{gemini-3-flash-\allowbreak preview}) for any LLM call, ChromaDB with the default embedding function for vector retrieval, the same LLM-as-Judge scoring (Section~\ref{sec:experiments}), and the same per-question reset (no cross-conversation leakage). The three published systems use heavier infrastructure---MongoDB$+$Elasticsearch$+$Milvus (MemMachine), Tempr / pgvector (Hindsight), or unspecified hybrid stores---which we deliberately replace with a minimal common stack to isolate the representation as the variable. Per-baseline source files in our release: \texttt{run\_locomo\_memmachine.py}, \texttt{evermemos\_lite.py}, \texttt{hindsight\_lite.py}.

\subsection{MemMachine (\texttt{run\_locomo\_memmachine.py}, \texorpdfstring{$\sim$245}{\textasciitilde 245} LOC)}

\textbf{Faithful to the description.} (i)~Episode-level storage: every conversation turn is indexed verbatim as a single sentence \texttt{[session\_id date] speaker: text}, and full-ordered episodes are kept for context expansion. (ii)~Nucleus retrieval: top-$k$ dense match with $k{=}30$. (iii)~Contextual expansion: $\pm 3$ surrounding sentences around each nucleus hit, deduplicated and re-ordered by original position. (iv)~The retrieved expanded context is passed verbatim to Gemini~3 Flash for answering.

\textbf{Approximated.} The MemMachine paper specifies neither the exact embedding model nor the rerank stage; we use ChromaDB's default embedding (\texttt{all-MiniLM-L6-v2}-equivalent) and skip cross-encoder reranking. The published system also pairs sentence-level with profile-level memory; we omit profile memory because the LOCOMO conversations are short enough that per-question retrieval already accesses the relevant content. Both omissions plausibly reduce our MemMachine score relative to the original paper.

\subsection{EverMemOS (\texttt{evermemos\_lite.py}, \texorpdfstring{$\sim$394}{\textasciitilde 394} LOC)}

\textbf{Faithful to the description.} The three-phase pipeline from the paper abstract: (i)~Phase~1 ``Episodic Trace Formation''---each session is segmented into MemCells, with an LLM extracting atomic facts and Foresight signals (predicted future information needs). (ii)~Phase~2 ``Semantic Consolidation''---MemCells are clustered into thematic MemScenes via similarity; a scene-level summary is produced and a User Profile of stable attributes is updated. (iii)~Phase~3 ``Reconstructive Recollection''---query embedding $\to$ MemScene-level filter (\texttt{SCENE\_TOP\_K=3}) $\to$ MemCell-level dense retrieval (\texttt{CELL\_TOP\_K=20}) $\to$ BM25 keyword channel (\texttt{BM25\_TOP\_K=20}) $\to$ rerank by recency and Foresight overlap (\texttt{FORESIGHT\_BOOST=0.5}) $\to$ atomic-fact aggregation $\to$ context assembly.

\textbf{Approximated.} The paper specifies neither the exact embedding model nor the clustering algorithm parameters; we use ChromaDB defaults and a similarity-threshold linkage clustering. Foresight signal extraction is implemented but the trigger threshold is a default we picked rather than one from the paper. We do not implement the long-horizon engram-decay schedule (the paper describes it as ``cell-level forgetting''); on a 5-conversation benchmark this affects nothing materially, but on month-long deployments it would.

\subsection{Hindsight (\texttt{hindsight\_lite.py}, \texorpdfstring{$\sim$420}{\textasciitilde 420} LOC)}

\textbf{Faithful to the description.} (i)~The 10-tuple Fact node \texttt{(subject, body, time, embedding, $\tau_s$, $\tau_e$, $\tau_m$, label, confidence, extras)} is built explicitly. (ii)~The four logical fact networks (World, Experience, Opinion, Observation) are constructed via labeled extraction. (iii)~Coarse-grained chunking of conversation turns into 2--5 facts per turn via an LLM extractor. (iv)~Four-channel retrieval: semantic (top 30), BM25 (top 30), graph spreading activation (2 hops, decay 0.6), and temporal proximity (top 30), all fused with Reciprocal Rank Fusion ($k{=}60$). (v)~Cross-encoder rerank with \texttt{cross-encoder/ms-marco-MiniLM-L-6-v2}, final 20 facts, packed within a 4000-token budget.

\textbf{Approximated / omitted.} (i)~The CARA disposition layer (controllable agent response affect) is omitted---it shapes the agent's voice and beliefs, not its retrieval. (ii)~Opinion formation/reinforcement (the paper's belief-update dynamics) is omitted; we keep facts as immutable records with a confidence field. (iii)~The published Tempr / pgvector store is replaced with ChromaDB plus an in-memory BM25 index. The paper's reported 91.4\% on LongMemEval uses a Gemini-3 \emph{Pro} backbone in the full pipeline; our 73.0\% on the full 500-question LongMemEval under Gemini-3 \emph{Flash} with the minimal infrastructure isolates the representation effect from those amplifying factors.

\subsection{Backbone caveat}

Gemini~3 \emph{Flash} is the smaller, lower-cost sibling of Gemini~3 Pro, and is generally weaker on long-context reasoning tasks. The published numbers for EverMemOS (GPT-4.1-mini), Hindsight (Gemini-3 Pro), and MemMachine (mixed proprietary backbones) are not directly comparable to ours; ours are most informative as a same-backbone, same-stack ranking of the architectural ideas, not as a final accuracy claim against those systems. UaC v5 runs under exactly the same handicaps as the baselines in our setup, so the relative gaps are interpretable.

\subsection{UaC v5 hyperparameters}

For completeness, the UaC v5 hyperparameters used throughout the paper are: extraction LLM Gemini~3 Flash, thinking budget 8192; structuring LLM Gemini~3 Flash, thinking budget 16384, no \texttt{max\_output\_tokens} cap; answer-time LLM Gemini~3 Flash, thinking budget 2048, temperature 1.0; vector store ChromaDB with cosine similarity and the default embedding; retrieval combines (a)~the structured Python state truncated to 6000 chars if longer, (b)~top-20 facts from the per-fact vector index, (c)~top-10 raw conversation excerpts from the archive index. Judge LLM Gemini~3 Flash, thinking budget 256.


\section{Additivity of SOTA Retrieval Mechanisms}
\label{app:additivity}

Section~\ref{sec:experiments} compares UaC v5 against MemMachine, EverMemOS, and Hindsight as standalone systems; the comparison is between representations under one backbone. A separate question is \emph{additivity}: if we keep UaC v5's structured-Python representation and \emph{also} add a SOTA retrieval mechanism on top, does the score improve?

\textbf{Setup.} We construct a UaC v5 + MemMachine variant (\texttt{user\_as\_code\_v5\_plus\_mm.py}) that retains UaC v5's three-channel retrieval (structured code, fact-vector, raw archive) and additionally appends a MemMachine-style episode context (sentence-level dense retrieval with $\pm 3$ contextual expansion, top-30 nucleus) as a fourth channel. Everything else is identical: same conversations (5-conversation LOCOMO subset, 300 QAs), same Gemini~3 Flash backbone, same judge, same prompts.

\textbf{Result.} The hybrid reaches \textbf{81.7\%} on the 5-conversation LOCOMO subset, vs.\ 78.0\% for plain UaC v5---a +3.7pp gain. McNemar's exact test on the per-question correctness gives $p{=}0.14$ (29 hybrid-only correct vs.\ 18 UaC-only correct out of 300), and Wilson 95\% CIs $[73.0, 82.3]$ vs.\ $[76.9, 85.7]$ overlap, so we treat this as a clear directional signal rather than a guaranteed effect at $n{=}300$.

\textbf{Interpretation.} The two mechanisms are partially complementary: structured Python state surfaces typed facts (dates, names, numbers), while episode retrieval surfaces the surrounding conversational context. The gain is concentrated in the two harder conversations (conv-41 +8.3pp, conv-43 +8.3pp) where plain UaC v5 was weakest, suggesting that episode context most helps when the structured state has compressed away the relevant detail. Per-conversation results: conv-26 75.0\%/75.0\% (tie), conv-30 90.0\%/93.3\% (+3.3pp), conv-41 80.0\%/88.3\% (+8.3pp), conv-42 76.7\%/75.0\% ($-1.7$pp), conv-43 68.3\%/76.7\% (+8.3pp). The cost is roughly doubled per query because the MM index is added on top of UaC's three existing channels; in practice an implementation should switch the MM channel on only when the structured state's similarity to the query is below threshold.

\textbf{(2)~Claude is uniformly slightly stricter, but the relative ranking is preserved and UaC's gaps over the lower systems widen.} On LOCOMO, Claude scores every system 2--6pp lower than Gemini; on LongMemEval, the difference is under 2pp. Importantly, the UaC--MemMachine gap on LOCOMO grows from $+6.1$pp under Gemini to $+7.5$pp under Claude, and the UaC--Mem0 gap grows from $+49.5$pp to $+52.4$pp. So the same-family judge is, if anything, slightly favorable to the lower-scoring competitors; the cross-family judge sharpens UaC's lead rather than erasing it.

\textbf{(3)~Cross-judge drops correlate with prediction ambiguity, not with system identity.} On LOCOMO, Mem0 has the largest drop ($-6.0$pp), MemMachine the second-largest, and the typed-state UaC~v5 sits in the middle. The pattern matches the intuition that predictions phrased as terse fragments (``yesterday'', short noun phrases) are more sensitive to judge generosity, while typed or fully-formed answers are less so.

The headline rankings on both LOCOMO and LongMemEval are stable under the cross-family judge---which is the load-bearing claim of this appendix. We treat this as evidence that the same-family judge does not materially distort the comparison.


\section{Phase-2 Failure-Mode Analysis}
\label{sec:phase2-failures}

Phase~2 is an LLM call: it can drop facts, produce non-parseable code, or store dates as strings instead of typed \texttt{date()} objects. We audit each of these failure modes by running Phase~2 on all five LOCOMO conversations and inspecting the generated typed Python. The four checks are: \emph{(i)~parse}---does the output parse as valid Python; \emph{(ii)~date typing}---are dates stored as \texttt{date(\dots)} rather than strings; \emph{(iii)~notes-bucket usage}---do facts that do not fit typed fields land in a \texttt{notes: list[str]} so they are still in the file; \emph{(iv)~dropped facts}---are there input facts whose distinctive content tokens (rare nouns, numbers, year-formatted dates) appear nowhere in the generated code, even in notes.

\textbf{Parseability.} Every generated file parses as valid Python (5/5). Phase~2 has not produced syntax errors on any LOCOMO conversation in our audit. This matters because the answer-time channel passes the structured state to the LLM verbatim; an unparseable file would silently corrupt the structured-state retrieval.

\textbf{Date typing.} Across all 5 conversations, the generated code contains 44 \texttt{date(\dots)} expressions and zero string-formatted dates. The 16-K-token thinking budget appears sufficient for the LLM to follow the explicit date-typing instruction reliably. This matters specifically for LongMemEval's temporal-reasoning category, which exercises date arithmetic.

\textbf{Dropped facts.} Across 10{,}273 distinctive-token facts, 18 are dropped (overall rate 0.18\%). All 18 are from conv-43, which has the largest fact corpus (2{,}553 facts) and produced the \emph{smallest} structured code (6{,}329 chars, vs.\ 12{,}222 for conv-30 with fewer facts). The pattern is consistent: when the structuring LLM is overloaded, it compresses by abstracting away atomic details rather than by losing structure or types. The 18 dropped facts are all from the same session (session\_27) and concern minor personal-state details (e.g., ``Tim finds learning German to be tough''). The notes bucket caught 423 facts that did not fit typed fields across the corpus---the safety net is doing its job.

\textbf{Implications.} Phase~2 has three failure axes: parse, type, content. The first two are clean on this benchmark (0/5 and 0/44 respectively). Content-loss is non-zero but small (0.18\% overall on the audited five conversations) and concentrated on the longest input. This bounds the headline LOCOMO gap to Full Context: of the 1.0pp UaC-vs-Full Context gap on the full 10-conversation benchmark (Section~\ref{sec:experiments}), at most $\sim$0.2pp is explained by Phase~2 dropping facts the question needed; the remainder is in the retrieval layer (channel ablation in Section~\ref{sec:channel-ablation}). At even larger scales the truncation behavior documented in Section~\ref{sec:phase2-scalability} would dominate over the LLM-level compression we see here, which is why we flag hierarchical structuring as the right scaling strategy.


\section{Phase-2 Structuring Cost at Scale}
\label{sec:phase2-scalability}

Phase~2 is a single LLM call that regenerates structured Python from the entire fact corpus accumulated so far. To measure how its cost behaves outside the 19-session LOCOMO range, we run Phase~2 on synthetically lengthened corpora at $\{19, 50, 100, 200\}$ sessions, seeded from the actual conv-26 Phase~1 fact list (1{,}569 facts) and extended by appending shadowed-prefix duplicates of the same fact list to bring the total to $\sim$82 facts/session at each scale. The duplication is a worst-case stress test: a real long-running deployment would partially compress, so these numbers are an upper bound on what naive all-at-once Phase~2 needs.

Three observations from Table~\ref{tab:phase2-scalability}:

\textbf{(1)~Output stays bounded.} Output tokens hold at $\sim$3{,}100--3{,}800 across the full $10\times$ range of input sizes, because the LLM increasingly groups and abstracts as input grows---a 200-session corpus is structured into the same dataclass schema as a 50-session corpus, just with longer collections.

\textbf{(2)~Input is the only growing cost component, and our implementation caps it.} At $n{=}19$ the input fits naturally (62K tokens, no truncation); by $n{=}100$ the 500K-character input cap engages and the input flattens at $\sim$200K tokens. Above that scale, our naive Phase~2 silently drops the tail of the fact list, which is exactly the limitation that motivates an incremental or hierarchical structuring strategy (Limitations, Section~\ref{sec:limits}).

\textbf{(3)~Wall time is roughly constant at 30--40 seconds} once the LLM's thinking step dominates. So in absolute terms, even on a 200-session deployment, Phase~2 is a sub-minute background operation, not a foreground latency item---but the truncation behavior means a production deployment shouldn't rely on naive regeneration past $\sim$100 sessions.

The clean linear regime (no truncation) is $n_{\text{sess}} \leq 50$: $0.78$~m\$ per session at $n{=}19$ and $1.30$~m\$ per session at $n{=}50$. Extrapolated naively, Phase~2 on a year of weekly sessions ($\sim$52 sessions) would cost $\sim$$\$0.07$ per regeneration. The cost is bounded by the LLM context, not by the number of facts.

\begin{lstlisting}[caption={Constraint from \texttt{constraints/financial\_authorization.py}: groups pending transfers by (recipient, amount, purpose) and flags any group with $>$1 distinct destination.},label={lst:app-finance-constraint}]
def check_financial_authorization(transfers: list[WireTransfer]) -> list[Alert]:
    groups: dict[tuple, list[WireTransfer]] = {}
    for t in transfers:
        if t.status != "pending":
            continue
        groups.setdefault((t.recipient_name, t.amount, t.purpose), []).append(t)

    alerts = []
    for (recipient, amount, _), group in groups.items():
        destinations = {(t.destination_institution,
                         t.destination_account_last_four) for t in group}
        if len(destinations) > 1:
            descs = [f"{t.destination_institution} (****"
                     f"{t.destination_account_last_four}) per {t.requested_by}"
                     for t in group]
            alerts.append(Alert(
                severity="critical", domain="finance",
                message=(f"CONFLICTING wire transfer instructions for "
                         f"${amount:,.2f} to {recipient}: " + " vs. ".join(descs) +
                         ". Verify with the account holder before sending.")))
    return alerts
\end{lstlisting}

Listing~\ref{lst:app-analytical-state} shows the typed state Phase~2 produces for a synthetic user with 200 dining records over two years. The key generalization: \emph{retrieval ranks; aggregation enumerates}. Any question whose answer depends on every relevant record (counts, sums, group-bys, time-window filters, top-$k$ within a population) is structurally outside what top-$k$ retrieval can solve. UaC's typed state lifts the question from natural language to one line of Python, where the interpreter handles enumeration for free. The 99\% vs.\ 43\% gap on the analytical benchmark (Table~\ref{tab:analytical}) is this same trace, repeated across 100 questions.

\subsection{Why these cases matter beyond the benchmark numbers}

The drug-allergy interaction in Figure~\ref{fig:teaser-check} and the wire-transfer conflict above are both real-deployment scenarios where the user is in genuine danger from agent error. They share a structure that no LOCOMO-style QA captures: \emph{the user never asks the question}. They depend on the agent noticing a constraint violation across facts surfaced in different sessions, by different people, possibly months apart. This is exactly the regime where a representation that supports executable boolean checks beats a representation that supports only similarity-ranked retrieval, and is why we built the Active Service benchmark (Section~\ref{sec:active-service}) as a distinct evaluation axis. The headline numbers---100\% on standard scenarios, 85\% on hard---are read most fairly with these scenarios in mind: each missed alert is a real harm avoided, not a ranking-list position.
