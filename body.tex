\section{Introduction}
\label{sec:intro}

To build truly personalized, continuous-service AI agents, a \emph{User Memory} system is indispensable. Memory is not simply recording every word a user says---it is gradually forming a model of the user through sustained interaction. This paper focuses on long-term user memory: persistent cross-session knowledge that accumulates over weeks and months of interaction.

User memory tasks span a spectrum of difficulty: (1)~\textbf{Basic Recall}---storing and retrieving unambiguous facts; (2)~\textbf{Multi-session Retrieval}---reasoning over information scattered across sessions, requiring disambiguation and conflict resolution; and (3)~\textbf{Active Service}---proactively synthesizing information to provide anticipatory, unsolicited help. Existing benchmarks~\citep{maharana2024locomo, wu2025longmemeval, hu2025memoryagentbench} primarily test the first two categories, but no benchmark tests the \emph{initiation asymmetry} central to Active Service: the system must generate alerts \emph{without being asked}, triggered by state changes rather than queries.

Current memory systems---vector databases, JSON stores, knowledge graphs, flat fact extractors---treat memory as a loose collection of facts. This creates two problems. First, conflicting facts (``I love cilantro'' vs.\ ``I actually hate cilantro'') coexist unresolved without version history. Second, even the most advanced formats cannot express executable rules like ``if passport expires within 180 days of travel date, raise an alert.''

\textbf{Thesis:} The fundamental limitation of free-text and fact-store formats is that they separate \emph{representation} from \emph{verification}. Typed Python unifies the two in the same medium: the same code that stores \texttt{passport.expiry\_date = date(2025, 2, 18)} can also express \texttt{assert (passport.expiry\_date - flight.departure\_date).days >= 180} (see Listings~\ref{lst:travel-state}--\ref{lst:constraint}). JSON dicts plus a Python REPL share this property in principle, but require LLM-managed parsing at every query (Section~\ref{sec:analytical}), which becomes unreliable on noisy real-world conversation. User as Code's contribution is the \emph{two-phase pipeline} that converts unstructured conversation into a representation a code tool can read directly.

\textbf{Three things you can do once memory is code.} Figure~\ref{fig:tiers} shows the three capability tiers UaC unlocks, all against the same tiny typed state and all expressible as one-line Python. (a)~\textbf{Recall} is attribute access. (b)~\textbf{Analytical inference} is a list comprehension---trivial in Python, structurally lossy under top-$k$ retrieval (this is the gap quantified in Section~\ref{sec:analytical}: UaC~v5 99\% vs.\ MemMachine 43\%). (c)~\textbf{Active service} is a boolean check over typed dates---one comparison the interpreter runs deterministically at every state change. Figures~\ref{fig:teaser-input}--\ref{fig:teaser-check} then expand (c) into a full life-safety walkthrough where the relevant facts arrive in two conversations ten months apart.

We model a user's entire memory as a \textbf{self-evolving software project} with typed dataclasses, domain packages, and executable constraints. The system uses a two-phase architecture: (1)~\emph{append-only fact extraction} that never loses information, and (2)~\emph{periodic code structuring} that organizes facts into typed Python. This enables a \textbf{generate-verify-review loop} where the coding agent writes constraints, the interpreter verifies them deterministically, and results surface as pre-computed alerts in a compact manifest.

Our contributions:
\begin{itemize}[leftmargin=*]
\item A two-phase memory architecture that achieves 78.0\% on the 5-conversation LOCOMO subset (300 QAs)---94.7\% of the full-context upper bound (82.3\%; gap not significant under McNemar, $p{=}0.12$) and ahead of three recent SOTA systems reproduced on identical Gemini~3 Flash backbone (MemMachine 75.3\%, Hindsight 70.0\%, EverMemOS 55.0\%)---while enabling 100\% proactive alert detection on the 40 standard Active Service scenarios (85\% on the 20 hard scenarios).
\item A novel Active Service evaluation protocol testing proactive alerting across 40 scenarios in 5 constraint categories.
\item \textbf{A new analytical-inference benchmark} (100 cases, 10 record types, $N \in \{20, 50, 100, 200, 500\}$) that exposes the gap between code-executable representations (UaC~v5: 99\%, Full~Context+REPL: 100\%) and retrieval-based ones (MemMachine: 43\%, Mem0: 6\%) on aggregate questions where top-$k$ retrieval is structurally lossy. We also report Gemini~3 Flash token cost per system: UaC~v5's structuring pays for itself after \texttildelow3 queries against the same user state, after which it costs an order of magnitude less than re-loading the records each query.
\item A comprehensive ablation showing that separating memorizing (append-only) from structuring (periodic code generation) is the key architectural insight.
\item A Modularity / Progressive Disclosure ablation (\modularityCases\ single-domain questions over a 10-domain, 500-record state) showing that loading only the query-relevant domain reduces prompt-token cost by 14.9$\times$ with no accuracy loss (98.0\% vs.\ 97.0\% monolithic), validating the principles for production scale.
\item Cross-LLM portability validated by re-running the full pipeline with GPT-5.4 (OpenAI) replacing Gemini~3 Flash, recovering 80.8\% on the 2-conversation LOCOMO subset (120 QAs; statistical tie with Gemini, McNemar $p{=}0.82$).
\item Open-source implementation with same-backbone comparisons against five existing memory systems---Mem0, A-MEM, MemMachine, EverMemOS, Hindsight---and full-context baselines on five benchmarks (LOCOMO, LongMemEval, Active Service, Analytical Inference, Modularity).
\end{itemize}


\section{Related Work}
\label{sec:related}

The field of LLM agent memory has experienced explosive growth in 2025--2026, with 20+ systems, 15+ benchmarks, and comprehensive surveys~\citep{hu2025memoryage, du2026memorysurvey, yang2026graphmemory}. We organize related work around three gaps.

\subsection{Gap 1: Representation Separates Storage from Verification}

All existing memory systems store user state in formats that cannot be directly executed. \textbf{Flat fact systems} like Mem0~\citep{chhikara2025mem0} extract atomic facts with CRUD lifecycle. \textbf{Structured note systems} like A-MEM~\citep{xu2025amem} use Zettelkasten-inspired notes with dynamic linking. ENGRAM~\citep{patel2025engram} shows careful typing with dense retrieval matches complex architectures. \textbf{Knowledge graph approaches} like Zep/Graphiti~\citep{rasmussen2025zep} build temporal KGs with bitemporal modeling; MAGMA~\citep{jiang2026magma} uses multi-graph traversal. \textbf{Hybrid architectures} like Hindsight~\citep{latimer2025hindsight} maintain four logical networks (91.4\% on LongMemEval); MemMachine~\citep{wang2026memmachine} stores entire episodes (0.9169 on LOCOMO). \textbf{OS-inspired systems} like MemGPT/Letta~\citep{packer2023memgpt} and MemOS~\citep{li2025memos} use programmatic infrastructure but represent state as text. LangMem~\citep{langmem2025} allows agents to update their own instructions---the closest to ``executable memory.'' In all cases, user state remains text or structured data, not executable code. \textbf{User as Code closes this gap.}

\subsection{Gap 2: No Benchmark Tests Proactive Memory-Triggered Alerting}

LOCOMO~\citep{maharana2024locomo} provides 1,986 QA pairs; LongMemEval~\citep{wu2025longmemeval} tests 500 questions across six question types. LoCoMo-Plus~\citep{li2026locomoplus} tests implicit constraints; MemoryArena~\citep{he2026memoryarena} shows LOCOMO-saturated agents fail in agentic settings. ProAgentBench~\citep{tang2026proagentbench} tests proactive task assistance but not memory-triggered alerting. PersistBench~\citep{pulipaka2026persistbench} identifies memory safety risks. \textbf{No existing benchmark tests the initiation asymmetry} central to Active Service.

\subsection{Gap 3: Memory Operations Are Not Yet Optimized End-to-End}

Memory-R1~\citep{yan2025memoryr1} trains memory policies with GRPO (+48\% F1). AgeMem~\citep{yu2026agemem} learns proactive summarization through progressive RL. Mem-alpha~\citep{wang2025memalpha} demonstrates generalization to 400K+ tokens. Cognitively-inspired systems include FadeMem~\citep{wei2026fademem} (biologically-inspired forgetting), LightMem~\citep{fang2025lightmem} (Atkinson-Shiffrin model), and EverMemOS~\citep{hu2026evermemos} (engram-inspired lifecycles, 93.05\% on LOCOMO). All train over custom memory APIs. \textbf{User as Code's file-system-based architecture makes memory operations native file actions}, directly compatible with RL training.

\subsection{Two-Phase Architecture}

Our key architectural insight, validated through ablation (Section~\ref{sec:ablation}), is that memorizing and structuring must be separated:

\textbf{Phase 1 --- Memorizing (per session, append-only):} For each conversation session, extract every individual fact as a flat string using a thinking-enabled LLM (Gemini 3 Flash, thinking budget 8192). Facts are appended to a running list---never overwritten, never deleted. Relative dates are resolved to absolute dates using session timestamps. This produces $\sim$50 facts per session, $\sim$950 total for a 19-session conversation. Facts are indexed in a vector database (ChromaDB) for retrieval.

\textbf{Phase 2 --- Structuring (periodic, from all facts):} Periodically, regenerate the entire structured Python code from the accumulated fact list. The LLM organizes all facts into typed dataclasses with proper type annotations: \texttt{date()} objects for dates, typed lists for collections, \texttt{notes: list[str]} fields for hard-to-type facts. The code size scales with the number of distinct facts: a 19-session LOCOMO conversation yields $\sim$7K characters of structured code (thinking budget 16,384), while the analytical-inference benchmark at $N{=}500$ records produces 50K--55K characters (thinking budget 8,192, no record truncation up to 500K input characters). Because the code is generated fresh from the complete fact corpus rather than incrementally, no information is lost during the transition between fact and structure.

\textbf{Archive (raw conversation).} Additionally, raw conversation chunks are stored in a vector database as a retrieval fallback when structured code and extracted facts lack sufficient detail.

\subsection{Design Principles}

Two principles are evaluated directly in this paper:

\begin{enumerate}[leftmargin=*]
\item \textbf{Separation of Structure and Data.} Schema (dataclasses) separated from state (instances). Validated by the v3$\to$v5 ablation (Section~\ref{sec:ablation}).
\item \textbf{Unified Representation and Verification.} Code serves as both storage and verification medium. Validated by Active Service (Section~\ref{sec:active-service}) and Analytical Inference (Section~\ref{sec:analytical}).
\end{enumerate}

Three further principles guide production deployment but are not isolated by the experiments:

\begin{enumerate}[leftmargin=*,start=3]
\item \textbf{Modularity by Life Domain.} Memory partitioned into independent domain packages (e.g., \texttt{travel/}, \texttt{health/}, \texttt{finance/}). Limits cross-domain leakage and supports selective loading at scale.
\item \textbf{Progressive Disclosure.} Compact manifest ($\sim$200--300 tokens, always loaded) with on-demand domain loading. Keeps the prompt budget bounded as the user state grows.
\item \textbf{Agent-Native File System.} User project is a directory in the agent's workspace---no custom memory API needed.
\end{enumerate}

\subsection{The Generate-Verify-Review Loop}

The core mechanism for Active Service:
\begin{enumerate}[leftmargin=*]
\item \textbf{Generate:} The coding agent writes Python constraints against the code-represented state.
\item \textbf{Verify:} Execute in a sandbox---results are deterministic.
\item \textbf{Review:} The agent reviews results, decides to refine, persist, or incorporate.
\end{enumerate}

When an ad-hoc check proves useful, the agent promotes it to a persistent constraint. Alerts surface in the manifest's \texttt{ACTIVE\_ALERTS}, visible at the start of every future conversation. Constraints emerge autonomously from the LLM's reasoning.

\subsection{Multi-Strategy Retrieval}
\label{sec:retrieval}

At query time, retrieval composes three channels rather than picking one. Each channel addresses a different failure mode of the others: the structured-code channel can return a typed object but only for facts the structuring step has captured; the fact-vector channel covers the long tail of facts that did not make it into the typed schema; and the raw-archive channel preserves the exact conversational phrasing for queries that hinge on wording.

\textbf{(1)~Structured code state.} The full \texttt{state.py} of the manifest-routed domain (or all domains, in the non-modular setting) is included verbatim in the prompt, truncated at 6{,}000 characters. The agent reads typed dataclass instances and the pre-computed \texttt{ACTIVE\_ALERTS} list with no parse step.

\textbf{(2)~Fact-vector retrieval.} A ChromaDB collection over the append-only fact list (one fact per record, $\sim$50 facts/session) is queried by cosine similarity against the question; the top 20 facts are appended. This recovers facts the structuring step compressed away or normalized to a different surface form.

\textbf{(3)~Archive retrieval.} A second ChromaDB collection holds the raw conversation chunked at session granularity; the top 10 chunks by cosine similarity are appended. Used as a last-resort fallback for direct-quote questions.

The three channels are concatenated under fixed section headers (\texttt{[STATE]}, \texttt{[FACTS]}, \texttt{[ARCHIVE]}) and the combined block is passed to the answer-time LLM. We do not rerank or weight across channels; the LLM treats them as three views of the same memory and the prompt instructs it to prefer the structured channel when sources conflict.


\section{Experiments and Evaluation}
\label{sec:experiments}

\subsection{Setup}

\textbf{LLM:} Gemini 3 Flash (\texttt{gemini-3-flash-preview}) with thinking enabled throughout. Answer generation uses thinking budget 2048. No \texttt{max\_output\_tokens} restriction.

\textbf{Evaluation:} LLM-as-Judge with binary correctness scoring (CORRECT/WRONG, thinking budget 256). The judge receives the question, gold answer, and prediction, and is instructed to be generous: answers conveying the same core information with different wording or format score CORRECT; answers score WRONG only when factually incorrect or claiming unavailability when the gold answer exists.

\textbf{Baselines:} Mem0~\citep{chhikara2025mem0} (flat fact extraction, mem0ai 1.0.5), A-MEM~\citep{xu2025amem} (Zettelkasten-inspired structured notes), Full Context (all raw text passed to LLM).

\textbf{Benchmarks:} \emph{All four memory systems are evaluated on the same data}: LOCOMO~\citep{maharana2024locomo} (5 conversations, 60 QAs each, 300 QAs total; conv-26, conv-30, conv-41, conv-42, conv-43); LongMemEval~\citep{wu2025longmemeval} (200 stratified questions, 40\% of the 500-question split, seed 42, with type distribution preserved: 54~temporal-reasoning, 53~multi-session, 31~knowledge-update, 28~single-session-user, 22~single-session-assistant, 12~single-session-preference); Active Service (40 standard + 20 hard scenarios).

\textbf{Cross-LLM portability.} To verify that User as Code's gains do not depend on a particular LLM's code-generation idiosyncrasies, we additionally re-run UaC~v5 with GPT-5.4 (OpenAI) replacing Gemini~3 Flash for fact extraction, code structuring, and answer generation. The Gemini~3 Flash judge is reused for fair scoring against the Gemini run. Cross-LLM evaluation uses the 2-conversation LOCOMO subset (120 QAs) for tractability.

\textbf{Statistical interpretation.} Headline accuracies are reported as the proportion of correct answers; for $n{=}300$ (LOCOMO) and $n{=}200$ (LongMemEval), the 95\% Wilson confidence interval has half-width $\sim$5--6pp at the relevant accuracy range. Per-system Wilson intervals for the LOCOMO headline numbers are: UaC~v5 $[73.0, 82.3]$, MemMachine $[70.1, 79.8]$, Hindsight $[64.6, 74.9]$, EverMemOS $[49.3, 60.5]$, A-MEM $[51.0, 62.2]$, Mem0 $[27.6, 38.2]$. Because all systems are evaluated on the \emph{same} questions, marginal Wilson intervals overstate the uncertainty of pairwise comparisons; we additionally report McNemar's exact test on the per-question correctness vectors. On LOCOMO, UaC~v5 is significantly better than Hindsight ($p{=}0.008$), EverMemOS, A-MEM, and Mem0 ($p{<}10^{-10}$ each), \emph{not} significantly different from MemMachine ($p{=}0.41$; UaC right on $40$ questions baseline missed, MemMachine right on $32$ UaC missed), and \emph{not} significantly different from the Full Context upper bound ($p{=}0.12$). On LongMemEval, UaC~v5 is significantly better than Hindsight ($p{<}10^{-4}$), A-MEM, and Mem0 ($p{<}10^{-12}$), and statistically tied with MemMachine ($p{=}1.0$), EverMemOS ($p{=}0.14$), and Full Context ($p{=}0.54$). The picture is therefore a three-way cluster (UaC, MemMachine, Full Context) at the top of LongMemEval, and a clearer UaC lead on LOCOMO.

On LOCOMO (Table~\ref{tab:locomo}), all systems are evaluated symmetrically on the same 5-conversation, 300-QA subset. UaC~v5 reaches \textbf{78.0\%}, recovering 94.7\% of the Full Context upper bound (82.3\%) while operating on extracted memory rather than the full transcripts; the 4.3pp gap to Full Context is not statistically significant under McNemar ($p{=}0.12$, 23 UaC-only correct vs.\ 36 Full-Context-only correct). A-MEM (56.7\%) and Mem0 (32.7\%) lose 21--45pp on the same data, both significant at $p{<}10^{-10}$. Inspection of the per-question failures shows Mem0's gap is dominated by temporal questions where its extracted memories preserve relative-date references (``yesterday'', ``last week'') without resolving them, and A-MEM's gap is dominated by single-hop detail questions where note-level retrieval surfaces only context summaries rather than the underlying turn content.

On LongMemEval (Table~\ref{tab:longmemeval}), the 200-question stratified sample (4$\times$ larger than the 48-question split used in earlier drafts) shrinks per-category variance and confirms the same ranking. UaC~v5 reaches \textbf{84.5\%}, within 2pp of Full Context (86.5\%), while A-MEM (58.0\%) and Mem0 (24.5\%) trail by 26--60pp. The typed \texttt{date()} fields help on knowledge-update (97\%~vs.~90\% for Full Context); the gap to Full Context is concentrated in temporal-reasoning (70\%~vs.~81\%), where the extraction step occasionally drops the timestamps required for date arithmetic over many sessions.

\textbf{Cross-LLM portability.} Replacing Gemini~3 Flash with GPT-5.4 throughout the UaC~v5 pipeline (extraction, structuring, answer generation) recovers \textbf{80.8\%} on the 2-conversation LOCOMO subset (120 QAs)---a 1.7pp gap from the Gemini run on the same subset (82.5\%). At $n{=}120$ the Wilson 95\% half-width is $\sim$7pp, so this difference is comfortably inside noise; we report it as evidence that the architecture transfers across the two largest closed-model families, not as a precise equivalence claim. McNemar's test on the per-question correctness on the same 120 questions gives $p{=}0.82$ (9 GPT-only correct, 11 Gemini-only correct), consistent with no detectable difference at this sample size.

\textbf{Comparison to recent SOTA systems.} We reproduce three recent SOTA systems---MemMachine~\citep{wang2026memmachine}, EverMemOS~\citep{hu2026evermemos}, and Hindsight~\citep{latimer2025hindsight}---on the \emph{same} 5-conversation LOCOMO subset and 200-question LongMemEval sample with the \emph{same} Gemini~3 Flash backbone, so any difference reflects representation rather than model. Our reimplementations follow the architectures described in each paper but use approximate prompts (the originals are not always published) and lighter infrastructure (ChromaDB rather than MongoDB+Elasticsearch+Milvus). Full reimplementation details---class structure, retrieval parameters, prompt templates, and what we matched vs.\ approximated---are in Appendix~\ref{app:reimpl}. On LOCOMO (Table~\ref{tab:locomo}): MemMachine reaches 75.3\%, Hindsight 70.0\%, EverMemOS 55.0\%---all numerically behind UaC~v5's 78.0\%, with the UaC--Hindsight, UaC--EverMemOS, and UaC--A-MEM/Mem0 gaps significant under McNemar but the UaC--MemMachine gap not significant ($p{=}0.41$). On LongMemEval (Table~\ref{tab:longmemeval}): MemMachine \emph{ties} UaC~v5 (\memmachineLME\ vs.\ 84.5\%, McNemar $p{=}1.0$), EverMemOS 79.5\% (also a statistical tie, $p{=}0.14$), Hindsight 70.5\% ($p{<}10^{-4}$). Inspecting the per-category breakdown is informative: MemMachine actually beats UaC on multi-session (85\% vs.\ 79\%) and temporal-reasoning (72\% vs.\ 70\%), where the answer is a coherent span of related turns that contextual sentence expansion surfaces well; UaC pulls ahead on single-session-preference (83\% vs.\ 67\%), where typed fields disambiguate from dense facts. \emph{Representations matter most where the answer is not a contiguous span}---LOCOMO has more such questions, hence the clearer separation there. The original papers report higher numbers (EverMemOS 93.05\% LOCOMO with GPT-4.1-mini; Hindsight 91.4\% LongMemEval with a Gemini-3 \emph{Pro} backbone in their full pipeline), but those settings differ in either the LLM, the retrieval stack, or both---so the original numbers should be read as the ceiling for those architectures, not as a direct comparison to ours. Two confounds shrink absolute scores in our setup: (i)~Gemini~3 \emph{Flash} is the smaller, lower-cost sibling of Gemini~3 Pro and is generally weaker on long-context reasoning, and (ii)~our retrieval stack is intentionally minimal (single ChromaDB collection, default embedding) to isolate the representational variable. These handicaps apply equally to UaC.

\subsection{Analytical Inference}
\label{sec:analytical}

A third capability tier sits between basic recall and proactive alerting: \emph{aggregate inference over the user's records}---answering questions like ``how many contacts did I meet during undergrad'', ``average dining spend in 2024 by cuisine'', or ``did my workout count increase from Q1 to Q2''. This is exactly the regime where a code-executable representation should pull ahead of free-text retrieval: counts, group-bys, time-window filters, and joins are one-line Python over typed objects but fundamentally lossy under top-$k$ retrieval.

\textbf{Benchmark construction.} We synthesize 100 cases spanning 10 record types (trips, contacts, meals, transactions, sleep log, workouts, books, medical visits, work meetings, purchases). Each type contributes 10 cases covering 10 question patterns (count, sum, average, group-by, time-window filter, multi-condition filter, top-$k$, min/max, threshold, year-over-year trend). Per-case record counts span $N \in \{20, 50, 100, 200, 500\}$ to surface scaling behavior. Ground truth is computed deterministically from the synthetic data, so scoring is exact-match (no LLM judge needed).

\textbf{Systems.} Five systems run on identical cases with Gemini~3 Flash backbone: Full Context (LLM in-head reasoning over raw JSON), Full Context + Python REPL (same data, plus \texttt{python} and \texttt{read\_file} tools so the LLM can compute), UaC~v5 (records structured into typed Python dataclasses, exposed via REPL), MemMachine~\citep{wang2026memmachine} (sentence-level retrieval with contextual expansion), and Mem0 (flat fact extraction). Mem0 and MemMachine retrieve top-20 entries and have the LLM reason over them.

The results (Table~\ref{tab:analytical} and Figure~\ref{fig:analytical-scaling}) split cleanly by representation class. \textbf{Retrieval-based memory collapses on aggregation}: MemMachine drops from 100\% at $N{=}20$ to 15\% at $N{=}200$ as more records become relevant than top-$k$ can return; Mem0 sits near zero throughout because its NL fact stores cannot be enumerated. \textbf{Full Context degrades when $N$ exceeds in-head capacity}: 100\% accuracy through $N{=}100$, dropping to 90\% at $N{=}200$ and $N{=}500$ as the LLM miscounts. \textbf{Adding a Python REPL solves counting completely} (FC+REPL: 100\% overall, perfect across all $N$). \textbf{UaC~v5 matches FC+REPL across the full $N$ range} (overall 99\%, perfect on $N \leq 200$, 95\% at $N{=}500$). The single $N{=}500$ failure is a corner case where Q1 and Q2 averages differ by 0.0012 hours of sleep duration---essentially a tie that the gold rule resolves as ``increase'' but is below the noise floor of the structured Python rounding.

Full Context degrades past $N{=}100$ (90\% at $N{=}200$ and $N{=}500$) as the LLM miscounts. The headline message is the divide between \emph{representations a code tool can read} (UaC~v5, FC+REPL, Full Context for small $N$) and \emph{representations only retrievable by similarity} (Mem0, MemMachine). The former scale with N; the latter do not. UaC~v5's specific advantage---typed objects enabling typed queries---matches a JSON+REPL baseline on this benchmark, because the analytical inputs are already structured. The contribution of UaC's two-phase pipeline is felt earlier: it converts unstructured conversation into the kind of representation a code tool can reason over, which is the prerequisite for analytical inference in real deployments.

\subsubsection{Token cost and amortization}

\input{body_cost_table}

We additionally instrumented every Gemini call with token counts and computed approximate USD cost using Gemini~3 Flash pricing (Table~\ref{tab:analytical-cost}). Three findings:

\textbf{(1)~On a single-query workload, FC+REPL is both more accurate and cheaper than UaC~v5}: $13.6$~m\$/case vs.\ $38.1$~m\$/case (2.8$\times$; total over 100 cases: \$1.36 vs.\ \$3.81). UaC's cost is dominated by the structuring step, which generates \texttildelow1M output tokens of dataclass code across 100 cases. FC+REPL's cost is dominated by re-including the records JSON in the LLM context every tool turn (4.2M input tokens).

\textbf{(2)~The cost story flips on multi-query workloads.} Structuring is paid once per user state; subsequent queries against the typed code cost only \texttildelow$1.4$~m\$/case (Table~\ref{tab:analytical-cost-amortized}). FC+REPL pays the full per-case cost \emph{every} query because it re-loads the records each time. With per-case structuring at ${C_s}$ and per-query costs $q_{\text{UaC}}$ and $q_{\text{FC+REPL}}$, $K$ queries against the same user state cost $C_s + K\,q_{\text{UaC}}$ vs $K\,q_{\text{FC+REPL}}$. At $N{=}500$, $C_s{\approx}102$~m\$, $q_{\text{UaC}}{\approx}1.4$~m\$, $q_{\text{FC+REPL}}{\approx}38$~m\$. The per-query cost ratio is $q_{\text{FC+REPL}}/q_{\text{UaC}}\approx27$$\times$ once structuring is paid; the breakeven point is $K = C_s/(q_{\text{FC+REPL}}-q_{\text{UaC}}) \approx 2.8$, so UaC pays back its structuring cost after the third query. Amortized over $K{=}100$ queries, total UaC cost is $244$~m\$/case vs FC+REPL's $3{,}780$~m\$/case---$15.5\times$ cheaper. The two ratios are different things ($27\times$ ignores structuring; $15.5\times$ amortizes it across 100 queries) and we use the amortized ratio in the headline claims.

The ablation (Table~\ref{tab:ablation}) reveals four key findings:

\textbf{Finding 1: Append-only extraction is the single biggest improvement.} v2$\to$v3 gains +19.0pp on LOCOMO. Never overwriting facts prevents information loss during incremental state updates.

\textbf{Finding 2: Code structure alone hurts recall if done incrementally.} v3$\to$v4 loses 10.0pp on LOCOMO. Each session's code rewrite drops earlier facts. The \texttt{notes} field (intended as a safety net) becomes an escape hatch---the LLM dumps facts as strings instead of typing them.

\textbf{Finding 3: Two-phase separation solves the overwrite problem.} v5 combines v3's coverage (append-only facts) with v4's code structure (typed dataclasses), gaining +12.3pp over v4 and +2.3pp over v3. \textbf{Finding 4: The constraint pipeline is orthogonal to LOCOMO QA.} Adding the constraint-generation pipeline on top of v5 leaves LOCOMO QA accuracy unchanged at 78.0\% but lifts Active Service alert detection from 67.5\% to 100\%. The pipeline is a separate read-time mechanism that operates over the same structured state; it does not affect retrieval quality.

\subsection{Modularity and Progressive Disclosure}
\label{sec:modularity}

We finally evaluate two design principles introduced in Section~\ref{sec:method} that the standard benchmarks do not isolate: \emph{Modularity by Life Domain} and \emph{Progressive Disclosure}. We synthesize a multi-domain user state with 10 domains (trips, contacts, meals, transactions, sleep, workouts, books, medical visits, meetings, purchases) at 50 records each (500 total), then ask 100 single-domain questions (10 per domain---the full question-pattern coverage from the analytical benchmark). Three loading strategies share the same Python REPL backend and Gemini~3 Flash model:

\textbf{Monolithic:} the full 300-record state is inlined into the LLM system prompt every query (the naive ``always-dump'' baseline).

\textbf{Modular:} only a list of available domain names is in the system prompt. The LLM calls a \texttt{load\_domain(name)} REPL helper to materialize the specific domain it needs.

\textbf{Manifest+routing:} the system prompt additionally contains a one-line summary per domain ($\sim$50 tokens each); the LLM uses the manifest to route then calls \texttt{load\_domain}.

The results (Table~\ref{tab:modularity}, Figure~\ref{fig:modularity}) sharpen the production case for Modularity. \textbf{Modular loading matches monolithic} on accuracy (98.0\% vs.\ 97.0\%, a 1-question difference at $n{=}100$ that is well inside the Wilson interval) at \textbf{14.9$\times$ lower cost} ($2.5$~m\$/case vs.\ $36.4$~m\$/case; total over 100 cases: \$0.25 vs.\ \$3.64). The intuition: at 500 records, dumping the full state into the system prompt every query exceeds the LLM's effective working window, and the model occasionally retrieves the wrong record from its own context. Loading only the query-relevant domain shrinks the prompt to $\sim$50 records and the model reads it cleanly. The Manifest+routing variant trades a brief-summary indirection for somewhat higher cost ($3.8$~m\$/case, total \$0.38) and loses 10pp accuracy because the LLM occasionally mis-routes from the one-line summaries. Monolithic cost grows linearly with state size, while modular cost is bounded by the largest single domain---a structural advantage as user state accumulates over time.

This ablation reverses a finding from the earlier 30-case version of this benchmark, where monolithic was perfect and modular trailed by 6.7pp: at small state sizes the in-prompt baseline does not yet hit its working-memory ceiling, so the apparent ``accuracy cost'' of modularity disappears as the state scales up. With accuracy now indistinguishable and cost an order of magnitude lower, the Modularity and Progressive Disclosure principles are \emph{Pareto-preferable} at the 500-record scale we test, and the cost gap should widen further at production scales of thousands of records.


\section{Discussion}

\textbf{SOTA retrieval mechanisms are partially additive.} We test this directly in Appendix~\ref{app:additivity}: a UaC v5 + MemMachine-style episode retrieval hybrid is run on the same 5-conversation LOCOMO subset. The hybrid reaches 81.7\% vs.\ plain UaC v5's 78.0\% (+3.7pp), with the gain concentrated on the two harder conversations (conv-41 and conv-43, both +8.3pp) where plain UaC v5 was weakest. McNemar's exact test gives $p{=}0.14$ (29 hybrid-only correct, 18 UaC-only correct), and Wilson 95\% CIs $[73.0, 82.3]$ vs.\ $[76.9, 85.7]$ overlap, so we report this as a clear directional signal rather than a guaranteed effect at $n{=}300$. The mechanisms drawn from MemMachine~\citep{wang2026memmachine} and EverMemOS~\citep{hu2026evermemos} can therefore be layered onto UaC's representation rather than competing with it---useful when the structured state's compression has dropped the detail the question needs.

\textbf{Domain knowledge is LLM-generated, infrastructure is human-designed.} Schemas, constraints, and domain partitioning are all produced by the LLM at write time and evolve with the user. What is human-designed is engineering infrastructure: the two-phase pipeline, the generate-verify-review loop, and the sandbox boundary. The interpreter is a \emph{tool} that the LLM uses, not a \emph{rule} the LLM must obey~\citep{sutton2019bitter}.

\textbf{Memory safety.} PersistBench~\citep{pulipaka2026persistbench} finds 53\% cross-domain leakage and 97\% sycophancy in persistent memory. User as Code provides natural mitigations: domain separation limits leakage, version control provides audit trails, and the explicit nature of code enables selective forgetting.

\textbf{RL-trainability.} Because memory operations are file-system actions, User as Code is directly compatible with RL-based memory training~\citep{yan2025memoryr1, yu2026agemem, wang2025memalpha}---file operations are natural actions RL can optimize.

\textbf{Limitations.}
\begin{itemize}[leftmargin=*]
\item \emph{Extraction overhead.} $\sim$4$\times$ write-path cost vs.\ flat facts, justified by read-time correctness and the multi-query amortization shown in Table~\ref{tab:analytical-cost-amortized}.
\item \emph{Constraint logic errors.} Correct computation does not guarantee correct logic; a buggy constraint will fire deterministically every time.
\item \emph{Residual gap to Full Context on LOCOMO.} UaC~v5 trails Full Context by 4.3pp (78.0\% vs.\ 82.3\%); inspection of failures shows the gap is dominated by single-hop minor details (specific book titles, exact early-session dates) that the extraction step occasionally compresses away.
\item \emph{Active Service depends on the pipeline.} Without pre-computed alerts, UaC drops to 52.5\%---the constraint pipeline is the decisive factor on this benchmark, not the representation alone.
\item \emph{Structuring scalability.} Phase~2 regenerates the entire structured code from the complete fact corpus; at hundreds of sessions, this may require incremental or hierarchical structuring strategies. The Modularity ablation (Section~\ref{sec:modularity}) is a partial step in that direction.
\item \emph{Analytical benchmark is synthetic.} Records are schema-clean; real-world deployments will have noisier, partially-typed data, which we expect to favor UaC~v5 over the Full~Context+REPL baseline (since the baseline's parsing fragility scales with data noise).
\item \emph{Single-query design favors FC+REPL.} The benchmark times one question per case; the amortization analysis (Section~\ref{sec:analytical}) shows UaC's structuring pays back after \texttildelow3 queries against the same user state.
\item \emph{Cross-LLM coverage is limited.} Portability is verified on Gemini~3 Flash and GPT-5.4 only; smaller code generators (e.g., 7--8B parameter models) may produce lower-quality structured code.
\item \emph{Reimplementation fidelity.} Our reproductions of MemMachine, EverMemOS, and Hindsight under the same Gemini~3 Flash backbone are minimal-faithful (Appendix~\ref{app:reimpl}); their original numbers, obtained with stronger backbones (GPT-4.1-mini, Gemini-3 Pro) and larger retrieval stacks (MongoDB+Elasticsearch+Milvus), should be treated as the ceiling for those architectures, not direct competitors to our same-backbone numbers.
\item \emph{Sandboxing required.} Storing user state as executable code requires sandboxed execution and strict isolation to prevent cross-user leakage or code injection.
\end{itemize}


\section{Conclusion}

User as Code transforms user memory from a passive database into a modular software project. Our two-phase architecture---append-only fact extraction followed by periodic code structuring---resolves the tension between coverage and structure that plagued earlier designs. The ablation shows each decision's impact: append-only extraction gains +19pp recall, while two-phase separation adds code structure without losing facts.

On standard benchmarks evaluated symmetrically across all systems on the same 5-conversation LOCOMO subset (300 QAs) and 200-question LongMemEval sample, UaC achieves 78.0\% on LOCOMO (94.7\% of the 82.3\% full-context upper bound, McNemar $p{=}0.12$) and 84.5\% on LongMemEval (within 2pp of full-context's 86.5\%), outperforming A-MEM and Mem0 by significant margins under McNemar ($p{<}10^{-10}$) and matching MemMachine on LongMemEval ($p{=}1.0$). Replacing Gemini~3 Flash with GPT-5.4 throughout the pipeline preserves performance (80.8\% on the 120-QA cross-LLM subset, statistical tie with the Gemini run). On Active Service, the constraint execution pipeline achieves 100\% proactive alert detection on standard scenarios and 85\% on hard multi-step-arithmetic scenarios---a capability that requires executable code representation and has no equivalent in existing memory systems.

\textbf{Future work.} Three directions follow naturally from the limitations enumerated above: (i)~incremental or hierarchical structuring strategies that scale beyond the all-at-once Phase~2 to hundreds of sessions, (ii)~RL-trained constraint generation that learns which checks are worth promoting from ad-hoc to persistent, and (iii)~integration with the SOTA episode-retrieval mechanisms whose additivity we already established (Appendix~\ref{app:additivity}).

Code, data, and evaluation scripts are available at \url{https://github.com/bojieli/UserAsCode}.

\section{Reimplementation Details for SOTA Baselines}
\label{app:reimpl}

This appendix documents what our reimplementations of MemMachine, EverMemOS, and Hindsight match faithfully versus what they approximate, so the same-backbone numbers in Table~\ref{tab:locomo} and Table~\ref{tab:longmemeval} can be interpreted with the right level of skepticism.

\subsection{Shared infrastructure}

All three baselines share the same evaluation harness with UaC v5: Gemini~3 Flash (\texttt{gemini-3-flash-\allowbreak preview}) for any LLM call, ChromaDB with the default embedding function for vector retrieval, the same LLM-as-Judge scoring (Section~\ref{sec:experiments}), and the same per-question reset (no cross-conversation leakage). The three published systems use heavier infrastructure---MongoDB$+$Elasticsearch$+$Milvus (MemMachine), Tempr / pgvector (Hindsight), or unspecified hybrid stores---which we deliberately replace with a minimal common stack to isolate the representation as the variable. Per-baseline source files in our release: \texttt{run\_locomo\_memmachine.py}, \texttt{evermemos\_lite.py}, \texttt{hindsight\_lite.py}.

\subsection{MemMachine (\texttt{run\_locomo\_memmachine.py}, $\sim$245 LOC)}

\textbf{Faithful to the description.} (i)~Episode-level storage: every conversation turn is indexed verbatim as a single sentence \texttt{[session\_id date] speaker: text}, and full-ordered episodes are kept for context expansion. (ii)~Nucleus retrieval: top-$k$ dense match with $k{=}30$. (iii)~Contextual expansion: $\pm 3$ surrounding sentences around each nucleus hit, deduplicated and re-ordered by original position. (iv)~The retrieved expanded context is passed verbatim to Gemini~3 Flash for answering.

\textbf{Approximated.} The MemMachine paper specifies neither the exact embedding model nor the rerank stage; we use ChromaDB's default embedding (\texttt{all-MiniLM-L6-v2}-equivalent) and skip cross-encoder reranking. The published system also pairs sentence-level with profile-level memory; we omit profile memory because the LOCOMO conversations are short enough that per-question retrieval already accesses the relevant content. Both omissions plausibly reduce our MemMachine score relative to the original paper.

\subsection{EverMemOS (\texttt{evermemos\_lite.py}, $\sim$394 LOC)}

\textbf{Faithful to the description.} The three-phase pipeline from the paper abstract: (i)~Phase~1 ``Episodic Trace Formation''---each session is segmented into MemCells, with an LLM extracting atomic facts and Foresight signals (predicted future information needs). (ii)~Phase~2 ``Semantic Consolidation''---MemCells are clustered into thematic MemScenes via similarity; a scene-level summary is produced and a User Profile of stable attributes is updated. (iii)~Phase~3 ``Reconstructive Recollection''---query embedding $\to$ MemScene-level filter (\texttt{SCENE\_TOP\_K=3}) $\to$ MemCell-level dense retrieval (\texttt{CELL\_TOP\_K=20}) $\to$ BM25 keyword channel (\texttt{BM25\_TOP\_K=20}) $\to$ rerank by recency and Foresight overlap (\texttt{FORESIGHT\_BOOST=0.5}) $\to$ atomic-fact aggregation $\to$ context assembly.

\textbf{Approximated.} The paper specifies neither the exact embedding model nor the clustering algorithm parameters; we use ChromaDB defaults and a similarity-threshold linkage clustering. Foresight signal extraction is implemented but the trigger threshold is a default we picked rather than one from the paper. We do not implement the long-horizon engram-decay schedule (the paper describes it as ``cell-level forgetting''); on a 5-conversation benchmark this affects nothing materially, but on month-long deployments it would.

\subsection{Hindsight (\texttt{hindsight\_lite.py}, $\sim$420 LOC)}

\textbf{Faithful to the description.} (i)~The 10-tuple Fact node \texttt{(subject, body, time, embedding, $\tau_s$, $\tau_e$, $\tau_m$, label, confidence, extras)} is built explicitly. (ii)~The four logical fact networks (World, Experience, Opinion, Observation) are constructed via labeled extraction. (iii)~Coarse-grained chunking of conversation turns into 2--5 facts per turn via an LLM extractor. (iv)~Four-channel retrieval: semantic (top 30), BM25 (top 30), graph spreading activation (2 hops, decay 0.6), and temporal proximity (top 30), all fused with Reciprocal Rank Fusion ($k{=}60$). (v)~Cross-encoder rerank with \texttt{cross-encoder/ms-marco-MiniLM-L-6-v2}, final 20 facts, packed within a 4000-token budget.

\textbf{Approximated / omitted.} (i)~The CARA disposition layer (controllable agent response affect) is omitted---it shapes the agent's voice and beliefs, not its retrieval. (ii)~Opinion formation/reinforcement (the paper's belief-update dynamics) is omitted; we keep facts as immutable records with a confidence field. (iii)~The published Tempr / pgvector store is replaced with ChromaDB plus an in-memory BM25 index. The paper's reported 91.4\% on LongMemEval uses a Gemini-3 \emph{Pro} backbone in the full pipeline; our 70.5\% under Gemini-3 \emph{Flash} with the minimal infrastructure isolates the representation effect from those amplifying factors.

\subsection{Backbone caveat}

Gemini~3 \emph{Flash} is the smaller, lower-cost sibling of Gemini~3 Pro, and is generally weaker on long-context reasoning tasks. The published numbers for EverMemOS (GPT-4.1-mini), Hindsight (Gemini-3 Pro), and MemMachine (mixed proprietary backbones) are not directly comparable to ours; ours are most informative as a same-backbone, same-stack ranking of the architectural ideas, not as a final accuracy claim against those systems. UaC v5 runs under exactly the same handicaps as the baselines in our setup, so the relative gaps are interpretable.

\subsection{UaC v5 hyperparameters}

For completeness, the UaC v5 hyperparameters used throughout the paper are: extraction LLM Gemini~3 Flash, thinking budget 8192; structuring LLM Gemini~3 Flash, thinking budget 16384, no \texttt{max\_output\_tokens} cap; answer-time LLM Gemini~3 Flash, thinking budget 2048, temperature 1.0; vector store ChromaDB with cosine similarity and the default embedding; retrieval combines (a)~the structured Python state truncated to 6000 chars if longer, (b)~top-20 facts from the per-fact vector index, (c)~top-10 raw conversation excerpts from the archive index. Judge LLM Gemini~3 Flash, thinking budget 256.

\begin{lstlisting}[caption={Constraint from \texttt{constraints/financial\_authorization.py}: groups pending transfers by (recipient, amount, purpose) and flags any group with $>$1 distinct destination.},label={lst:app-finance-constraint}]
def check_financial_authorization(transfers: list[WireTransfer]) -> list[Alert]:
    groups: dict[tuple, list[WireTransfer]] = {}
    for t in transfers:
        if t.status != "pending":
            continue
        groups.setdefault((t.recipient_name, t.amount, t.purpose), []).append(t)

    alerts = []
    for (recipient, amount, _), group in groups.items():
        destinations = {(t.destination_institution,
                         t.destination_account_last_four) for t in group}
        if len(destinations) > 1:
            descs = [f"{t.destination_institution} (****"
                     f"{t.destination_account_last_four}) per {t.requested_by}"
                     for t in group]
            alerts.append(Alert(
                severity="critical", domain="finance",
                message=(f"CONFLICTING wire transfer instructions for "
                         f"${amount:,.2f} to {recipient}: " + " vs. ".join(descs) +
                         ". Verify with the account holder before sending.")))
    return alerts
\end{lstlisting}

The analytical-inference benchmark (Section~\ref{sec:analytical}) measures the gap between code-executable and retrieval-only representations on aggregate questions. This subsection traces one such question end-to-end against UaC v5 and a retrieval baseline so the structural reason for the gap is concrete.

Listing~\ref{lst:app-analytical-state} shows the typed state Phase~2 produces for a synthetic user with 200 dining records over two years. The key generalization: \emph{retrieval ranks; aggregation enumerates}. Any question whose answer depends on every relevant record (counts, sums, group-bys, time-window filters, top-$k$ within a population) is structurally outside what top-$k$ retrieval can solve. UaC's typed state lifts the question from natural language to one line of Python, where the interpreter handles enumeration for free. The 99\% vs.\ 43\% gap on the analytical benchmark (Table~\ref{tab:analytical}) is this same trace, repeated across 100 questions.

\subsection{Why these cases matter beyond the benchmark numbers}

The drug-allergy interaction in Figure~\ref{fig:teaser-check} and the wire-transfer conflict above are both real-deployment scenarios where the user is in genuine danger from agent error. They share a structure that no LOCOMO-style QA captures: \emph{the user never asks the question}. They depend on the agent noticing a constraint violation across facts surfaced in different sessions, by different people, possibly months apart. This is exactly the regime where a representation that supports executable boolean checks beats a representation that supports only similarity-ranked retrieval, and is why we built the Active Service benchmark (Section~\ref{sec:active-service}) as a distinct evaluation axis. The headline numbers---100\% on standard scenarios, 85\% on hard---are read most fairly with these scenarios in mind: each missed alert is a real harm avoided, not a ranking-list position.
